# Wayfinder — Design & Technical Decisions

Log format: date, decision, rationale, status (Approved / Provisional / Rejected / Needs owner approval).

---

## 2026-10-14 — D-001 Repository layout
**Decision:** The repository root is the Unity project root (per Blueprint §15.3): `Assets/Wayfinder/…`, `Packages/`, `ProjectSettings/`, `Docs/`, `Tools/`. Original specification documents stay at repository root unchanged.
**Rationale:** Matches the blueprint's declared structure and keeps docs/tools visible next to the project.
**Status:** Approved (implementation-side).

## 2026-10-14 — D-002 Engine baseline
**Decision:** Unity 6.3 LTS (`6000.3.x`), C#, URP, Input System, Addressables, Unity Test Framework, Newtonsoft JSON (`com.unity.nuget.newtonsoft-json`, free official package). No ad/IAP/analytics/multiplayer SDKs.
**Rationale:** Blueprint §15 baseline; Newtonsoft avoids fragile hand-rolled JSON for canonical save serialization.
**Status:** Approved (per spec).

## 2026-10-14 — D-003 No Unity/.NET toolchain in this environment
**Decision:** This implementation environment has **no Unity editor, no C# compiler, no Android/iOS toolchain** (only Python 3.11 and Node). All C# source, asmdefs, tests and editor scripts are produced as *compilable-intended real source* and labelled **Implemented (uncompiled/unverified)**. Python-based validation, content generation and economy simulation run in this environment and are labelled **Verified (data layer)**. Unity-side evidence (compilation, PlayMode, device builds) is **Blocked on owner toolchain** per handoff "If tools are unavailable".
**Rationale:** Handoff forbids fabricated build logs or false verification. Smallest missing tool to advance: an installed Unity 6.3 LTS editor (any `6000.3.x` patch) on the owner's machine; second: Android SDK/NDK or macOS+Xcode for device smoke builds.
**Status:** Approved (required honesty rule).

## 2026-10-14 — D-004 Editor/version pin policy (deviation from Blueprint §15.2 "record at M0")
**Decision:** `Packages/manifest.json` is committed with **provisional package pins** for the 6000.3 stream and `ProjectSettings/ProjectVersion.template.txt` instead of a fabricated `ProjectVersion.txt` patch number. `Tools/Build/pin_toolchain.py` stamps the real editor version once an editor is installed. The first open of the project in the chosen editor resolves packages, writes `ProjectVersion.txt` and `packages-lock.json`, which the owner commits.
**Rationale:** The blueprint forbids inventing package versions/patch numbers; this sandbox cannot query Unity's package registry (network is restricted to GitHub/npm/PyPI). Provisional pins are explicitly flagged and one command re-pins them.
**Status:** Provisional — owner must run `pin_toolchain.py` (or edit `Packages/manifest.json`) on first setup. Requirement BUILD-01 stays **Blocked** until then.

## 2026-10-14 — D-005 Input actions loaded from JSON at runtime
**Decision:** `WayfinderControls.inputactions` is committed as authored JSON and `InputRouter` builds the `InputActionAsset` via `InputActionAsset.FromJson` (Resources TextAsset). No generated C# wrapper dependency on `.meta` importer settings.
**Rationale:** Keeps input functional even before the importer generates wrapper code; avoids GUID/meta coupling in a hand-authored repo. Equivalent bindings and rebinding behaviour.
**Status:** Approved.

## 2026-10-14 — D-006 Scenes generated by editor setup script
**Decision:** Bootstrap, Title, PhysicsTestGround and VerticalSlice greybox scenes are created by `Tools → Wayfinder → Setup Project` (`Assets/Wayfinder/Scripts/Editor/SceneBuilder.cs`), which also wires URP/quality/player settings. Hand-writing `.unity` YAML with fabricated script GUIDs is rejected as fragile.
**Rationale:** Editor setup scripts are explicitly allowed by the handoff; programmatic scene building is deterministic and reviewable.
**Status:** Approved.

## 2026-10-14 — D-007 Pure domain core without UnityEngine references
**Decision:** Game rules that the blueprint requires to be unit-testable (stable hashing/PRNG, stat resolver, powertrain/fuel/damage formulas, inventory, economy ledger, transactions, missions, discovery/map, research, save envelope/atomic file protocol, chunk streaming state machine, route graph) live in code with **no UnityEngine dependency**, mirrored into `Assets/Wayfinder/Scripts/Core|Progression|Persistence|World` domain classes. UnityEngine-facing adapters (WheelCollider, Addressables, MonoBehaviours) wrap them.
**Rationale:** Blueprint §16 "explicit small services and pure testable domain logic"; enables the same logic to be exercised by NUnit EditMode tests and kept honest.
**Status:** Approved.

## 2026-10-14 — D-008 Content is data-first JSON with ScriptableObject import
**Decision:** Canonical content definitions are JSON under `Assets/Wayfinder/Content/` (auditable, generator-friendly, per §17.1 "backed by exportable JSON/CSV"). `ContentImporter` (editor) converts to ScriptableObjects and computes a catalog hash. Validators run headlessly (Python) and in-editor (C#).
**Rationale:** Enables full release-scope content (100 landmarks / 200 caches / 20 missions / 30 contracts / 20 tiers / 4 vehicles / 10 camps / 5 garages / 25 relics) to be complete, validated, and counted here.
**Status:** Approved.

## 2026-10-14 — D-009 World greybox bake approach
**Decision:** Deterministic height function (StableHash-seeded ridged/fractal noise + biome masks + authored road/river constraints) in pure C# (`Wayfinder.World`), editor `WorldBaker` bakes 256 m chunk greybox meshes/colliders and seam reports. Canonical seed `481516`, generator version `1` (§7.1).
**Rationale:** §7 hybrid pipeline; deterministic and testable without device access. Full authored dressing remains M5 content work.
**Status:** Approved (greybox = M3 scope).

## 2026-10-14 — D-010 Save JSON via Newtonsoft with canonical checksum
**Decision:** Save envelope per §17.3, payload serialized to canonical JSON (sorted keys, invariant culture) and SHA-256 checksum over canonical payload bytes. Atomic protocol: temp file → parse-verify → backup rotation → replace (`File.Replace` with same-filesystem fallback). Settings live in a separate file.
**Rationale:** §17.3/17.4 requirements; checksum detects accidental corruption; canonical form makes the checksum stable across dictionary ordering.
**Status:** Approved.

**Decision:** (a) C# NUnit EditMode/PlayMode suites committed for Unity Test Runner; (b) Python `Tools/Validation/validate_content.py`, `formula_checks.py`, `Tools/Balance/economy_sim.py` executed in this environment as real evidence for the data/formula layer. C# results remain unverified here.

## 2026-10-14 — D-014 Headless C# verification harness with pinned provenance
**Decision:** Add `Tools/Build/headless_cs.py`, which bootstraps a real Roslyn 3.9.0 `csc` (C# 9, the Unity 6 language level) on a .NET Core 3.1.23 runtime, builds Newtonsoft.Json 13.0.3, NUnit 3.13.3/NUnitLite and a .NET Standard 2.1 reference assembly from source, and then (a) compiles every non-Unity assembly with the real `.asmdef` reference graph at `-warn:4`, (b) runs the EditMode NUnit suites, (c) recompiles the runtime assemblies against **only** the .NET Standard 2.1 reference (Unity's API profile), (d) parse-checks the Unity-dependent files. Every artifact is pinned by commit/tree hash or SHA-256 and comes only from the hosts reachable here (GitHub, PyPI). Run outputs go to `Logs/headless/` (ignored); cited results are copied under `Docs/evidence/`.
**Rationale:** D-003 forbade calling C# "Verified" without a compiler. Rather than keep guessing, obtain a real compiler within the egress policy. The harness is explicitly *not* a Unity build (KI-016) and `Implemented`→`Verified (headless)` is only claimed for assemblies that compiled, passed the profile check and executed their tests.
**Alternatives rejected:** Building Mono from source (hours, needs OpenSSL build); .NET SDK from the npm mirror (its 2.0 runtime needs `libunwind.so.8`, absent); vendoring compiler binaries into the repo (size, licensing).
**Status:** Approved. Evidence: `Docs/EVIDENCE_CS_HEADLESS.md`.

## 2026-10-14 — D-015 `SurfaceType` lives in `Wayfinder.Core`
**Decision:** The `SurfaceType` enum moved from `Wayfinder.Simulation` (`SurfaceTable.cs`) to `Wayfinder.Core` (`Core/SurfaceType.cs`). `SurfaceTable` and all consumers are unchanged apart from `using Wayfinder.Core;`.
**Rationale:** `Wayfinder.World` consumed the enum but its asmdef does not (and per ARCH-01 should not) reference `Simulation`; the headless compile exposed this as CS0246. Surface identity is a shared vocabulary term, which is what `Core` is for.
**Status:** Approved.

## 2026-10-14 — D-016 EditMode tests must not require `UnityEngine` to locate content
**Decision:** `ContentCatalogTests` resolves `Assets/Wayfinder/Content` via `UnityEngine.Application.dataPath` only under `UNITY_5_3_OR_NEWER`; otherwise via `WAYFINDER_CONTENT_DIR` or walking up from the test assembly to the repository root. Suites in `Wayfinder.Tests.EditMode` stay free of `UnityEngine` unless a test genuinely needs the engine.
**Rationale:** Keeps the EditMode suites runnable both in the Unity Test Runner and headlessly (D-014).
**Status:** Approved.

## 2026-10-14 — D-017 Save serialization uses explicit `SaveJson` settings
**Decision:** All `SaveService` serialize/deserialize/verify calls go through the `SaveJson` settings: `ReadSettings` = invariant culture, `ObjectCreationHandling.Replace`, `DateParseHandling.None`, `MissingMemberHandling.Ignore` (forward-compatible reads); `WriteSettings` = invariant culture, `DateParseHandling.None`, indented. `CanonicalJson` (checksum input) also parses with `DateParseHandling.None` so ISO timestamps are never re-formatted.
**Rationale:** Newtonsoft's default `ObjectCreationHandling.Auto` appends arrays into pre-initialised `List<T>` fields, which doubled every list on parse-verify and made the checksum fail on 100 % of saves (KI-013). Explicit settings make the save format independent of DTO field initialisers and of Newtonsoft defaults between versions.
**Status:** Approved.

## 2026-10-14 — D-018 `ResearchService` takes an injected story-gate predicate
**Decision:** `public ResearchService(Func<string, bool> isMissionCompleted = null)`; when null it falls back to `MissionService.Global`. `ResearchService.Global` keeps the fallback. The composition root may pass `MissionService.Global.IsCompletedCode` explicitly.
**Rationale:** The implicit static dependency made research tests order-dependent and hid the coupling; injection is the smallest change that keeps the no-monolith rule (ARCH-02) and makes the gate testable in isolation.
**Status:** Approved.

## 2026-10-15 — D-019 `Wayfinder.Campaign`: engine-free composition root and expedition lifecycle
**Decision:** Add `Assets/Wayfinder/Scripts/Campaign/` (`Wayfinder.Campaign.asmdef`, `noEngineReferences: true`, refs Core/Simulation/World/Progression/Persistence/Newtonsoft). `CampaignSession` owns **one instance per save slot** of every progression service (economy, inventory, discovery, missions, research, garage, contracts, transactions, clock, damage), maps them to/from `SavePayload` (`CampaignSnapshot`), and implements the §2.3 lifecycle (new game, depart, field actions, extraction, rescue). `SliceFieldController` turns per-frame vehicle telemetry into prompts/discovery/checkpoints/arrival; `HudModel`/`GarageModel`/`SummaryText` produce UI strings. MonoBehaviours (`CampaignHost`, `TitleFlowHost`, `VerticalSliceDriver`) only render and forward input. `TransactionService` receives its collaborators through `TransactionDependencies`; there is no fallback to `ResearchService.Global` any more (amends D-018; the `Global` instances remain only for legacy callers).
**Rationale:** The session needs both Progression and Persistence, must be testable headlessly (D-014) and must not become a Unity "GameManager" (ARCH-01/02). §15.3 lists folders but not this layer; a separate assembly keeps the asmdef graph acyclic (Platform/Presentation/Editor → Campaign → Persistence → Progression).
**Status:** Approved (implementation-side).

## 2026-10-15 — D-020 Snapshot persistence: commit-or-rollback critical operations, debounced field progress
**Decision:** The campaign is persisted as one snapshot. **Critical** operations — new game, depart, extraction/banking, full rescue, research, crafting, mission accept, camp establishment, camp deposit, relay activation, quest-item pickup — mutate memory, write + verify a new revision, and only then acknowledge; if the write fails, memory is restored from the pre-operation snapshot and the caller receives `FailureReason.SaveIoFailure` (HUD notices raised inside are discarded). **Field progress** (cache pickups, landmark discovery, map reveal, inspections, checkpoints, cargo moves, pose/fuel telemetry) marks the session dirty; `AutosavePolicy` saves 15 s after the first unsaved change (≥ 10 s between saves, 20 s retry after a failure, unscaled time). Suspend/quit saves immediately when dirty. `SaveService` gained a null-by-default `StepHook` test seam so interruption can be injected after every persistence step.
**Rationale:** §12.4/§16.2/§17.4 require "old or new complete state" and "never claim success". Snapshot saves make consistency structural: a crash inside the debounce window loses the pickup *and* keeps the cache uncollected, so nothing duplicates. 15 s sits inside §16.2's 10–20 s window.
**Status:** Approved.

## 2026-10-15 — D-021 Additive save fields at schema 1 + derived transaction sequence
**Decision:** `SavePayload.nextTransactionSequence` and `ExpeditionDto.stats` were added without bumping `CurrentSchemaVersion` (still 1). On load the next sequence is `max(nextTransactionSequence, highest ":<n>" suffix in appliedTransactionIds + 1)`, so payloads without the field cannot reissue an applied id. Transaction ids are `<expedition-or-hub-scope>:<global sequence>`.
**Rationale:** No public build or save exists, reads ignore unknown members and missing fields default safely; a reused id would turn a legitimate new pickup into a silent idempotent no-op (proven by `TransactionSequence_SurvivesReload_NoSilentIdCollision` and the mutation check). **Once any build ships, every further field change must bump the schema and add a migration (§17.5).**
**Status:** Approved; revisit at first public release.

## 2026-10-15 — D-022 Onboarding and recovery rules in the campaign layer
**Decision:** (a) A new game starts with **Q01 already accepted** and a `tutorial.active` flag that clears when Q01 completes. (b) Accepting a mission pre-satisfies objectives already true in the persistent world (landmark discovered, camp active, relay active, protected item held, map %) so a late accept can never dead-lock a one-time objective. (c) Full rescue = drop 25 % of loose `salvage_bundle` (rounded down) and then run the normal extraction at the nearest unlocked garage (banks the remainder and escrow, turns in ready missions, refuels/repairs); it is **free while the tutorial flag is set and in Relaxed Exploration**. (d) Mission objectives are routed by typed condition (`ReportCondition`), and `TraverseCheckpoints` only counts the next checkpoint in order.
**Rationale:** §2.3 "teaches the loop in under ten minutes", §5.6 "free in the tutorial", §1.4 "Relaxed: no reward punishment", §2.5 "missions never regress". Ordered checkpoints need no extra persisted state and cannot be inflated by re-driving a gate after a reload.
**Status:** Approved (design interpretation; owner may tune).

## 2026-10-15 — D-023 Hub settlement, storage and module simplifications for the slice
**Decision:** Items have a settlement category: Currency (`salvage_bundle`) banks 1:1; Materials (scrap/polymer/electronics/alloy) move to hub storage; Consumables (fuel can, repair kit, tire patch, boards, camp kit) and mission objects stay loaded as the loadout; protected-ledger objects never move. Garage storage is unlimited (10 000 slots / 10⁶ kg); camps share **one** 500 kg camp store (the v1 save has a single `campStorage`); materials that do not fit stay in cargo — nothing is lost. Researched modules are treated as installed (no slot-equip UI yet), which is what `ResearchService.ApplyTo` already assumed. The starting loadout is loaded into cargo.
**Rationale:** "Loose cargo is converted or stored" (§2.3) without forcing the player to re-load supplies every trip. Per-camp storage + hub-transfer UI and module slots (§10.2) are deferred (KI-028); they need a schema change.
**Status:** Provisional — revisit with the full garage UI.

## 2026-10-15 — D-024 Vertical-slice manifest and world-coordinate greybox
**Decision:** `Content/vertical_slice.json` defines the §21.3 slice: area x∈[512,1536), z∈[1792,2816) centred on `garage.home`; landmarks forest.01–06 (all *Gentle*; 01 and 06 are vistas); twelve caches (6 small / 4 standard / 2 remote, each ≥ 60 m from the garage yard and ≥ 10 m apart, chosen so the slice supplies the second camp kit's materials); Q01–Q04; tiers 1–6; two camp sockets, the creek-gauge inspect target, two ford checkpoints, the relay-fuse site, `relay.forest` and greybox features. Landmark/cache positions come from content `positionHint` (single source); the manifest authors only placements content leaves unset (camp sockets are `(0,0,0)` in `camps.json`). `SceneBuilder` generates the VerticalSlice scene in **world coordinates** from this data; `ProjectSetup` copies the campaign JSON into `Resources/Content` (git-ignored, generated). `validate_content.py` and `CampaignFieldTests` enforce scope, containment, reachability of every slice objective and affordability (income without mapping 3436 ≥ 3130 spend).
**Rationale:** One data source drives tests, validator and scene. The placeholder positions are compact (KI-027) but legal; M3 route validation may move them without changing ids.
**Status:** Approved for the greybox slice.

## 2026-10-15 — D-025 Exploration map: engine-free CPU raster, incremental redraw, texture upload
**Decision:** The map (§8.1, §13.2, §13.4) is drawn in plain C# (`Campaign/Map/`), not by a camera or shader. `ExplorationMap` owns a `MapRaster`: an RGBA32 byte array covering a window of map cells. The slice uses its 16 × 16 cells at 32 px/cell (2 m/px, 512², 1 MB); the whole 96 × 96 mainland later uses 8 px/cell (768², 2.4 MB; capped by `MapRaster.MaxTexturePixels`). Rows are bottom-up so Unity's `Texture2D.LoadRawTextureData` uploads the bytes verbatim (`Presentation/MapTextureBinding`). `Refresh()` diffs the session's revealed/surveyed `BitGrid`s against the drawn copies, 64 cells per word compare (`BitGrid.CollectDifferences`), and redraws only changed cells plus their *revealed* neighbours, which carry the soft fog edge. Fogged cells depend on nothing, so incremental and full redraws are byte-identical (tested; mutation-checked). An optional per-call cell budget spreads a vista reveal over frames; Unity uses 24 cells/frame and uploads at most every 0.25 s while cells remain queued. Fogged cells render as a blank survey sheet (parchment grain + 256 m grid). Revealed cells show surface colour × NW hillshade. Surveyed cells add 2 m contours. One `IMapTerrainSource` feeds both the map and reveal occlusion (D-028), so the map never shows relief the reveal ignored. The minimap is a `RawImage.uvRect` crop of the same texture: no second texture, no render-to-texture.
**Rationale:** Deterministic and headless-testable (pixels are asserted in NUnit and dumped to PNG evidence), cheap on mobile (no extra camera; 2 Hz reveals touch ~10–25 cells), and independent of the scene, which has no real terrain yet (KI-027/KI-029). A window keeps slice fidelity high without a 9 MB full-world texture.
**Status:** Approved (implementation-side). Device texture-upload cost unmeasured (KI-031).

## 2026-10-15 — D-026 Map spoiler policy (what the map may show)
**Decision:** (a) A new game's sheet is fully fogged. It shows only you, the home garage and the current mission's search circle. (b) **Unopened caches are never drawn**, even in revealed cells (§1 "map icons never reveal everything", §7.6); opened caches are drawn. (c) An undiscovered landmark appears as an unnamed *"Unconfirmed landmark"* ring once its cell is revealed (its silhouette has been seen); the name appears on discovery. (d) A `DiscoverLandmark` objective shows a 110 m search circle. Its centre is offset deterministically (`StableHash`) by 25–100 % of 0.45 × radius, so it always contains the landmark but never pinpoints it. (e) Mission-given sites (inspect target, the *next* ford checkpoint, camp socket, quest-item site, relay) are pinned while the objective is pending, because the briefing names the place. (f) Unlocked garages and active camps (safe hubs) are always drawn; locked garages, empty camp sockets and offline relays appear once their cell is revealed. (g) Only vertical-slice content is considered, so the map never hints at sites the scene lacks. (h) The tracked marker is the HUD's tracked objective (`ObjectiveText.TrackedLine` rule); a mission ready to turn in tracks its garage.
**Rationale:** The blueprint wants discovery to feel earned while missions stay readable (§2.3 onboarding under ten minutes). Search circles follow §8.3 "search areas" without the precise sensor rings (not in scope yet).
**Status:** Approved (design interpretation; owner may tune radius/offset).

## 2026-10-15 — D-027 Custom map markers: additive save fields at schema 1
**Decision:** `WorldStateDto` gains `customMarkers` (`MapMarkerDto` id/x/z/label, placement order), `nextCustomMarkerIndex` and `routeTargetMarkerId`, still at `CurrentSchemaVersion` 1 under D-021. `MapMarkerService` (Progression) allows **at most ten** markers (§13.4); the 11th returns `OverCapacity`. Ids are `marker.N`, and N is never reused within a save. Labels are trimmed, stripped of control characters and capped at 24 characters; empty labels default to "Waypoint N". Restore is tolerant: it drops malformed, duplicate and out-of-bounds entries and anything past ten, and lifts the next index above every surviving id. Placing, removing and routing are **field progress** (debounced autosave, D-020), not critical saves; they work in the garage and while the map pauses an expedition. Rescue never touches markers or revealed cells (§8.1).
**Rationale:** Markers are player annotations with no economic value. Stable ids keep a replayed command from retargeting another marker. Additive fields are safe because no build has shipped. **Bump the schema with any change after first release (§17.5).**
**Status:** Approved.

## 2026-10-15 — D-028 Reveal line-of-sight parameters, surveyed-flag fix, 2 Hz cadence
**Decision:** `World/TerrainLineOfSight` implements §8.1's "cheap terrain line-of-sight samples to avoid revealing behind major ridges", with these parameters:
- eye height 2 m (6 m from a vista viewpoint); target height 2 m;
- a cell is hidden only if terrain rises **> 4 m** above the sight line ("major ridge");
- samples every 16 m, at most 32;
- cells within 48 m are always revealed (the cell under the car can never stay fogged);
- unknown heights (NaN) never occlude.

The reveal path is `DiscoveryService.RevealVisibleAround`, called by `CampaignSession.RevealAround` for drive and vista reveals; heights come from `CampaignSession.MapTerrain` (the slice greybox profile, KI-029). **Fix:** vista *surveyed* flags now obey the same filter; before, a cell behind a ridge could be "surveyed" without being revealed. `SliceFieldController.RevealIntervalSeconds` changes from 1 s to **0.5 s** (§16.2 "map reveal 2 Hz"); the ≥ 16 m travel gate is unchanged, so a parked car does no work.
**Rationale:** The 4 m tolerance stops bumps and props from punching holes in the map. The slice's 8 m hill already hides part of its far side from Firewatch Nine. Reveals happen every 0.5 s **or** 16 m of travel, whichever comes later. At slice speeds the 16 m gate dominates (≈ 1.2 s at 50 km/h), and the 2 Hz cap only binds above ≈ 115 km/h. Either way the frontier stays far inside the 96 m radius.
**Status:** Approved; retune the tolerance with the baked M3 heightfield.

## 2026-10-15 — D-029 Field supplies and selling in the campaign session
**Decision:** `CampaignSession.Supplies` exposes the §5.5/§5.6/§10.3/§10.4 rules.
- **Fuel can:** usable only during an expedition, with ≥ 1 L missing. It adds `min(6, capacity − fuel)`. If any of the can would be wasted, the caller must confirm (`acceptWaste`); otherwise the result is `Cancelled` and nothing changes. The UI arms on the first tap and uses on the second. A partly used can still costs one item.
- **Repair kit:** +35 to one chosen subsystem, only while stopped (≤ 1 km/h) and out of water. It refuses a subsystem at 100, so a kit is never wasted. An engine repair ends a water-stall incident.
- **Tire patch:** v1 models a puncture as the tire-condition band < 30 (`DamageModel.PunctureThreshold`, already what `VehicleController` used). A patch lifts tires to 30: the 25 km/h cap goes, but the below-50 grip penalty stays until a free garage repair. No new save state is needed.
- Every successful use is one idempotent `UseItem` transaction. `TransactionService` consumes exactly one consumable and rejects non-consumables. Supply use is field progress (debounced autosave, D-020).
- **Selling:** only at a garage, one source at a time (garage storage or loaded cargo), 40 % of purchase price rounded down per unit. It never sells Salvage bundles (they bank 1:1), protected-ledger objects or mission cargo. It keeps as many camp kits as pending `EstablishCamp` objectives need, so Q03's free kit cannot be sold out from under the mission. A sale changes banked Salvage, so it is a **critical** operation (verified save, rollback on write failure). The garage UI asks for a confirming second tap.

**Rationale:** These follow the blueprint rules directly. Refusing wasteful uses and requiring a confirmation protect players from irreversible mistakes (§13 error states).
**Status:** Approved (implementation-side); the puncture band is a v1 simplification.

## 2026-10-15 — D-030 Researched stats reach the physics rig (KI-025 partial) and two composition fixes (KI-032)
**Decision:**
- `CampaignSession.ConfigureResolver(VehicleStatsResolver)` clears a resolver and applies exactly the researched modules, so repeated calls cannot double-apply (QA case 8). `ResolveStats()` (garage display) uses it.
- `VehicleController` exposes its own resolver (`StatsResolver`). `VerticalSliceDriver.ApplySessionToVehicle` configures it after load, research, extraction and supply use. From then on every stat the rig resolves includes research: wading depth, fuel drain, tank capacity, grip baseline, torque.
- The rig clamps fuel to the **resolved** capacity, so the driver no longer widens `spec.FuelCapacityLiters` at runtime.
- Two defects found while wiring this are fixed (KI-032): `VehicleStatsResolver.GripFor` now composes Trail Tires I (`DirtGravelGrip` ×1.10) on packed dirt/gravel for the all-terrain set only (§11.1 tier 1 + note), and `Powertrain` scales the torque curve by `stats.PeakTorqueNm / spec.PeakTorqueNm` (Engine Tune).
- **Deferred to M1 calibration:** WheelCollider friction still uses the resolver's packed-dirt baseline for all four wheels; per-wheel surface grip only scales braking. In physics the Trail Tires bonus therefore applies on every surface; the garage display is exact. Suspension travel/clearance research is not yet applied to WheelCollider geometry.

**Rationale:** One authoritative resolver configuration for display and driving (§11.2). Per-surface friction changes vehicle feel and interacts with the mud traction model, so it needs in-editor tuning, not blind edits.
**Status:** Approved; KI-025 stays open for the calibration items.

## 2026-10-15 — D-031 Input System repinned 1.12.0 → 1.20.1 (the cloud build's only error)
**Decision:** `Packages/manifest.json` pins `com.unity.inputsystem` **1.20.1**. The blueprint's 1.12.0 pin cannot compile on Unity 6000.3.26f1: its `InputSystem/Editor/InputSystemPluginControl.cs(47,25)` references `BuildTarget.ReservedCFE`, an enum member Unity 6000.3 removed, so every cloud build aborted with `error CS0117` (run 38754979851, `Docs/evidence/cloud-build-2026-10-15/`). Verified against the upstream package source (`Unity-Technologies/InputSystem`): the reference is replaced by the literal `(BuildTarget)49` from **1.13.1** onwards. 1.20.1 (2026-10-05) is the newest 1.x and the first whose `package.json` declares `"unity": "6000.0"`, i.e. built for the Unity 6 stream this editor belongs to. Fallback ladder if a run disproves it: **1.16.0** (first release with an explicit "fixed warnings on Unity 6.3" entry) → 1.14.2 → 1.13.1. Never 1.12.0 or 1.13.0.
**Rationale:** This is exactly the case D-004 anticipated — a provisional pin that a real editor rejects, to be replaced by "the nearest compatible version for the 6000.3 stream" and recorded here. The jump is bigger than the minimum fix (1.13.1) on purpose: the failure mode was *editor API drift inside a package*, and a package written for Unity 6 is less likely to contain other 6000.3 drift than one from February 2025. Wayfinder's own Input System surface is small and stable across 1.x (`Keyboard`, `Gamepad`, `PointerEventData`, `Accelerometer`, `Gyroscope.current.angularVelocity`, `InputSystemUIInputModule`, `InputActionAsset`/`InputActionMap`), so the API-drift risk to our code is low. No `com.unity.inputsystem` 2.x exists, so there is no major-version cliff.
**Status:** Approved; **not yet executed** (KI-036). One `workflow_dispatch` run settles it.

## 2026-10-16 — D-034 Scatter spacing and streaming hysteresis (M3, Batch G)

**Decision:**
- **Scatter (§7.6):** the world is tiled by a candidate grid whose cells tile each 256 m chunk exactly. Cell size is `256 / floor(256 / spacing)`, which is ≥ the minimum spacing, so each candidate is owned by one chunk and confined to its cell. Each candidate's randomness is `StableHash.CandidateSeed(ChunkSeed(owner chunk, layer), globalIndex)` (§7.3). A candidate is accepted when it is eligible (density draw, height band, slope, road-edge clearance, not reserved) and no eligible candidate within the spacing has a higher `(priority, index)`. Two accepted points are therefore never closer than the spacing, and neighbouring chunks agree at their borders because each candidate is computed from its global index alone. Trees use a 1 m road clearance; other species set their own.
- **Activation (§18.3):** the 3 × 3 ring around the player's chunk is always instantiated. Outside it, a chunk is instantiated when its rectangle is within **256 m** of the player and kept until **384 m**. Distances are measured from the player to the chunk rectangle, not in chunk indices. This is the metre-based "unload farther than the load threshold" rule in §18.3, extended to instantiation.
- **Data retention:** a chunk that leaves the activation band but stays within **640 m** is deactivated and keeps its data (`Deactivating → DataReady`, a new legal transition in `ChunkStateMachine`). It is unloaded only beyond 640 m.
- **Worst cases (asserted by tests):** instantiated ≤ 4 × 4 during a crossing, retained data ≤ 6 × 6.

**Rationale:** Chunk-index hysteresis was tested first and failed. A one-chunk move shifts the whole keep window, so oscillating across a boundary deactivated about three chunks per crossing (1218 deactivations in 400 crossings). Metre bands measured from the player do not move when the player jitters across a border. Dormant retention keeps re-entry free of IO. The 4 × 4 instantiated worst case is a deliberate trade against the 3 × 3 wording in §18.3: the 3 × 3 ring is still always active, and the extra column exists only while the player is crossing or retreating.

**Status:** Approved (implementation-side). Measured on the analytic test surface only. The 4 × 4 instantiated bound is an owner-review item, to be confirmed on device against the frame budget (KI-038, KI-037).


## 2026-10-16 — D-035 The job log is the Unity log, and diagnostics may never be silent

**Decision:**
- **The editor log is fetched, not hoped for.** game-ci's `build.sh` starts Unity with
  `-logfile /dev/stdout` and appends `customParameters` *after* it, so Unity's log is the GitHub
  Actions **job log**. A new reporting job (`diagnose`, `needs: apk`, `if: always()`,
  `permissions: actions: read`) runs `Tools/Build/fetch_job_log.sh "Build Wayfinder-dev.apk"`,
  which downloads that finished job's plain-text log from
  `GET /repos/{owner}/{repo}/actions/jobs/{job_id}/logs`, and reruns
  `Tools/Build/report_unity_failure.sh` over it. The current workflow uploads the raw log at
  `error_logs/unity-job-log.txt` in the `Wayfinder-APK-error-logs` artifact (renamed from the
  earlier `Unity-job-log` artifact). The dead `customParameters: -logFile …` override is removed
  from both Unity steps.
- **`report_unity_failure.sh` is never silent.** It always annotates which files it inspected and
  their sizes; it distinguishes a real editor log from Unity's auxiliary worker logs and says so;
  it is told how the Unity steps ended (`UNITY_SETUP_OUTCOME`/`UNITY_BUILD_OUTCOME`/
  `UNITY_JOB_RESULT`) and also infers failure from the log; and when a failure matches no pattern
  it emits an explicit error plus a 40-line, percent/newline-encoded log tail. New patterns: an
  unresolvable `-executeMethod`, any `*.Exception:` line, and this project's own breadcrumb.
- **Editor entry points leave a breadcrumb.** `Assets/Wayfinder/Scripts/Editor/EditorFailureLog.cs`
  wraps `ProjectSetup.Setup` and the four `BuildCommands` entry points: a thrown exception is
  appended to `Logs/wayfinder-editor-failure.log` (collected by the `Unity-logs` artifact and
  matched by the reporter) **and rethrown**, so Unity's exit code remains the verdict.
- **The runner is pinned to `ubuntu-24.04`.** Run 38875757162 carried GitHub's notice that the
  `ubuntu-latest` label migrates to Ubuntu 26 from 2026-10-19.

**Rationale:** run 38875757162 failed for eight minutes and produced two annotations, neither of
them a cause (KI-039). D-033 assumed Unity leaves an `Editor.log` in the workspace; it does not,
and the globbed worker logs made "nothing to report" indistinguishable from "nothing went wrong".
A diagnostic that can be silent is not a diagnostic. Fetching the job log needs no new third-party
action, only `actions: read` on the workflow token, and keeps the annotations API — the one host
this environment can reach — as the single place a failure is read from. The breadcrumb covers the
case the API cannot: it survives in the workspace artifact even if the job log is unavailable.

**Status:** Approved; executed locally only. 86/86 Python tests and 17/17 mutations caught
(`Docs/evidence/cloud-build-2026-10-16/`); **no part of it has run in CI yet** — the next owner
dispatch is what proves it, and what finally names the Unity failure (KI-041).


## 2026-10-19 — D-036 Fetch Unity's log past gh's escape-sequence guard, and treat absence as evidence

**Decision:**
- **Download through a chain, then sanitise whatever arrives.** `fetch_job_log.sh` tries `curl`
  first (it writes bytes verbatim, follows the API's 302 to the signed log URL, and is immune to
  gh's guard), then `gh api … --allow-escape-sequences`, then plain `gh api` for versions too old
  to know the flag. gh ≥ 2.63 refuses a raw non-JSON body carrying terminal escape sequences — and
  redirecting stdout does **not** bypass the guard (`!isJSON && !opts.AllowEscapeSequences &&
  bodyWriter != io.Discard`, `pkg/cmd/api/api.go`). The chain is PR #15's; the half it was missing
  is that **verbatim is not parsable** (next bullet), so the two are complementary rather than
  alternative fixes and were merged rather than chosen between.
- **The saved log is sanitised plain text.** CSI/OSC sequences, lone `ESC` and `\r` are stripped
  before anything parses the file: they split the exact lines the reporter greps for
  (`error CS0117:`, `Aborting batchmode due to failure:`) and GitHub's workflow-command parser
  rejects `ESC` in annotation text. The intermediate-byte class is `[ -/]` (space..slash), never
  `[ -\/]` — a backslash is not an escape inside a POSIX bracket expression, so `[ -\/]` means
  space..backslash and ate real log text (`ESC[KAborting…` → `orting…`).
- **Report what sanitising removed, and keep the tail.** The byte delta is printed, so a sanitiser
  that ever eats content is visible; a 400-line/400-char `.excerpt` rides up in
  `Wayfinder-APK-error-logs`, because annotations carry a few hundred characters and the cause of a
  hard stop is the last thing Unity said. The verbatim download stays in a temp file: a failing
  Unity job log runs to tens of MB and uploading it twice buys nothing.
- **A killed editor is a named cause.** New reporter patterns for `Crash!!!`, native stacktraces,
  `Fatal Error!`, OOM-killer/`Killed process`/cgroup-OOM, fatal signals, core dumps and
  `No space left on device` — deliberately narrow, because Unity also logs benign
  `Received signal SIGUSR1` and "out of memory" retry lines that must not be mistaken for a cause.
- **Absence is evidence.** `EditorFailureLog` writes `Logs/wayfinder-editor-failure.log` before an
  entry point rethrows, so when a Unity step failed and that file does not exist, the reporter now
  says so: no C# exception was thrown inside the build method, so the cause is earlier (compile
  error, package resolution, licence, unresolvable `-executeMethod`) or the process was killed.
  This is stated only where Unity actually ran (a `Logs/` directory exists) — never in the diagnose
  job's fresh checkout, where it would be a statement about nothing.
- **The refusal notice names a cause, not a scapegoat.** Its advice is now derived from the error
  text: an escape-sequence refusal says to check the runner's `gh` version, a real
  403/404/scope error mentions `actions: read`, and anything else points at the Actions tab. The
  old blanket "Needs `actions: read`" is what sent three investigations after a permission the
  workflow had already granted.
- **Do not warm the `Library` cache yet.** `actions/cache@55cc834` declares `post-if: "success()"`,
  so no `Library` cache can be saved until a run succeeds (KI-042). Saving one from a *failed*
  import via `actions/cache/save` + `if: always()` was considered and rejected: it would introduce
  an uncontrolled variable into a diagnosis that is not finished. Revisit after the first success.

**Rationale:** runs 39139527909, 39141218150 and 39141401948 each failed identically and each
diagnose job printed the same refusal twelve times. D-035 built the right mechanism and its tests
stubbed a permissive `gh`, so the guard was invisible from this environment — the notice even
misattributed the failure to a missing `actions: read` that was already granted, sending three
investigations after a non-problem. The refusal text is the evidence; gh's source confirms the
mechanism; a dress rehearsal reproduces it with the base-commit fetcher and shows the current one
annotating a compile error from the same stub.

**Status:** Approved; executed locally only. 91/91 diagnostics tests, 23/23 pipeline tests, 19/19
mutations caught for this batch and 22/22 for Batch H, dress rehearsal green over both download
paths (`Docs/evidence/cloud-build-2026-10-19/`). **No part of it has run in CI.** The Unity root
cause is no longer unknown: PR #15, merged while this batch was in flight, found that
`ContentImporter.cs` uses `Newtonsoft.Json.Linq` while `Wayfinder.Editor.asmdef` did not reference
`Unity.Newtonsoft.Json` — a CS0234 that aborts batchmode before `-executeMethod`, which is exactly
the shape KI-034 predicted and the run data showed (5–6 min, shader logs present, no breadcrumb).
That fix is reasoned from the source, not yet executed by Unity, and other errors may hide behind
it; one owner dispatch now both tests it and, if it fails again, reports why in file/line/col.

## D-037 — How the DEF-001…DEF-025 defects were closed (2026-10-19)

**Decision.** Every defect in `Docs/AI_BUG_REPORT.md` is fixed in code and pinned by a test. Six
design choices had to be made where the report left the fix open, and they are recorded here
because content and save compatibility are involved:

1. **A garage unlocks when the player reaches it (DEF-003).** `UnlockGarage` is a real command,
   executed by `TransactionService` inside `Extract()` before the "is it unlocked?" check. Free
   (§11.4 — garages never charge). Rationale: Q05's objective is `VisitVolume(garage.canyon)`, and
   `VisitVolume` is reported only by a successful extraction, so *any* rule that requires the garage
   to be unlocked first deadlocks the chain. Reaching a place to open it is also the only rule that
   needs no new currency sink.
2. **The 23 mission sites no catalog defined are authored in `Content/sites.json` (DEF-003).**
   `relay.*` uses the §6.1 region relay anchors from `WorldConstants` — `"provenance":
   "spec-anchor"`. The other 19 are placed by `Tools/Content/author_missing_sites.py` on a
   golden-angle spiral around their biome anchor — `"provenance": "procedural"`. They are editable
   data, not level design; the generator is deterministic so regenerating is safe.
3. **`document.pump_diagram` is a real item (DEF-003).** Q14 collects it, but it existed in neither
   `items.json` nor `ItemCatalog`, so the objective could never complete. Added to both (1 unit,
   1 kg, not sellable).
4. **Contract rewards are escrowed, not granted (DEF-007).** `CompleteContract` claims the reward
   key through `ClaimedRewardLedger` and calls `Economy.Escrow`, so payment is exactly-once and is
   banked with the next extraction like every other pending reward. The old
   `ContractService.Complete(...)` direct-grant path is kept for the tests that pin it, marked as
   legacy, and is not used by gameplay.
5. **Escrow is keyed by hub (DEF-017).** `Economy.Escrow(amount, hubId)` plus
   `BankEscrow(hubId)`: a bank releases the unattributed pool and that hub's own share, never
   another hub's. Rewards earned in the field (mapping, landmarks, contracts) stay unattributed on
   purpose, so they remain bankable at any hub — the reported symptom was a *hub-tagged* reward
   being swept by an unrelated bank, and this keeps banking convenient while fixing that.
   `wallet.escrowByHub` is additive, so an older save loads with everything unattributed.
6. **The countable mask is baked deterministically and persisted (DEF-008).** Measured first: the
   mainland macro heightfield spans 131–415 m, so **no** map cell is below sea level and the
   land-only rule leaves all 9,216 cells countable — the "counts ocean" symptom is not reproducible
   in this world. What was really broken is that the mask was written as `""` on every save and
   `WorldBaker` had no way to install a refined one. Both are fixed (`SetCountableMask`, and the
   mask now round-trips); the bake is correct and future-proof if the world gains water.

**Rationale.** The report's own fix column offered "implement X **or** scope it out" for several of
these. Scoping out 16 of 20 missions would have made `IMPLEMENTATION_STATUS.md` honest by making
the game smaller; authoring the missing sites makes it honest by making the content exist, which is
what the mission table already assumed. Where a value had to be invented (site positions), it is
marked in the data and generated by a checked-in script rather than typed by hand.

**Status:** Executed locally. 188/188 EditMode tests, `validate_content.py` clean,
`formula_checks.py` clean, `unity_type_check.py` 12/12, and the original bug probe now fails 10/15
(the intended inversion). Evidence: `Docs/evidence/bug-report-2026-10-19/`. The Unity-facing fixes
still need one real Unity run (KI-034).

## D-038 — How the AI-processing issue directory was triaged (2026-10-20)

**Decision.** The eight `SYS-*` entries in the attached `AI Processing Format.md` were checked against
the code at `HEAD` and answered individually in [AI_PROCESSING_TRIAGE.md](AI_PROCESSING_TRIAGE.md).
Five changed code; three did not, and the reasons are recorded here because each one looks like an
omission if only the diff is read:

1. **No `IdleBurnRate` multiplier (SYS-SIM-002).** The drain formula is specified in §5.1 with a QA
   example that is already pinned by a test; multiplying it by an idle factor would change specified
   behaviour to fix a symptom the blueprint already solves. `FuelModel.AutoStopIdleSeconds` existed
   unread, so the §5.1 rule — auto-stop after 15 s parked, then zero consumption because the engine
   is off — was implemented instead. The formula, the example, and every fuel test are unchanged.
2. **No Job System / `Task.Run` rewrite of chunk streaming (SYS-WRD-001).** `ChunkStreamPlanner` is a
   pure state machine with a per-step activation budget and no `Update()`; it cannot reference Unity,
   and its host MonoBehaviour does not exist yet (KI-034). A Jobs rewrite would be Unity-only code
   that neither the headless harness nor a PlayMode run could exercise here, and the reported
   synchronous work is not present to move.
3. **The map's polling was removed where it actually was (SYS-WRD-002).** `MapMarkerService` never
   polled. The 0.25 s full marker rebuild lived in `MapPresenter.Tick`. Rather than delete that timer
   (it also refreshes the player arrow, which moves every frame), a domain-level
   `CampaignSession.MapRevision` counter was added and the presenter rebuilds when it changes, so a
   committed marker or discovery is visible on that frame and the timer only serves the arrow.
4. **`schemaVersion` is kept; `saveVersion` is not added (SYS-SAV-002).** Same type, same role, and
   renaming would rewrite every existing save for a naming preference. The requested
   `ISaveMigrator` contract *was* added, with `FromVersion` + `Apply(JObject)` and lambda steps; the
   substantive defects — a missing step silently relabelling a save, and a mid-pipeline failure
   leaving a half-applied payload — are fixed and tested.
5. **JDK/NDK are pinned transitively, not by a host step (SYS-CICD-001).** Unity builds Android with
   the JDK/NDK inside its own editor image, so `actions/setup-java` on the runner would change
   nothing while looking like a pin. `UNITY_VERSION` pins the image and therefore the toolchain; the
   API *levels* are now pinned in `ProjectSetup` (authoritative) and in the workflow, with a test
   that fails if the two numbers disagree. The workflow comments say exactly this rather than
   implying a pin that does not exist.

**Rationale.** The handoff's rule is to implement actual source and never to claim verification that
does not exist. Three of the eight entries describe mechanisms this repository already had
(temp-file + atomic replace, schema version + migration hook, `MapMarkerService` without polling); a
diff that "fixed" them again would be noise, and a rewrite that cannot be compiled or run would be a
regression risk disguised as diligence. Where the reported symptom *was* real but the named file was
not the cause, the fix went to the layer that actually held the defect, and the reported file was left
alone.

**Status:** Approved (implementation-side). Deviations 1, 2 and 4 are visible to the owner in
`AI_PROCESSING_TRIAGE.md` §9; no product rule in the blueprint is changed.
