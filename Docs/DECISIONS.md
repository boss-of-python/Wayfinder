# Wayfinder — Design & Technical Decisions

Log format: date, decision, rationale, status (Approved / Provisional / Rejected / Needs owner approval).

---

## 2026-10-14 — D-001 Repository layout
**Decision:** The repository root is the Unity project root (per Blueprint §15.3): `Assets/Wayfinder/…`, `Packages/`, `ProjectSettings/`, `Docs/`, `Tools/`. Original specification documents stay at repository root unchanged.
**Rationale:** Matches the blueprint's declared structure and keeps docs/tools visible next to the project.
**Status:** Approved (implementation-side).

## 2026-10-14 — D-002 Engine baseline
**Decision:** Unity 6.3 LTS (`6000.3.x`), C#, URP, Input System, Addressables, Unity Test Framework, Newtonsoft JSON (`com.unity.nuget.newtonsoft-json`, free official package). No ad/IAP/analytics/multiplayer SDKs.
**Rationale:** Blueprint §15 baseline; Newtonsoft avoids fragile hand-rolled JSON for canonical save serialization.
**Status:** Approved (per spec).

## 2026-10-14 — D-003 No Unity/.NET toolchain in this environment
**Decision:** This implementation environment has **no Unity editor, no C# compiler, no Android/iOS toolchain** (only Python 3.11 and Node). All C# source, asmdefs, tests and editor scripts are produced as *compilable-intended real source* and labelled **Implemented (uncompiled/unverified)**. Python-based validation, content generation and economy simulation run in this environment and are labelled **Verified (data layer)**. Unity-side evidence (compilation, PlayMode, device builds) is **Blocked on owner toolchain** per handoff "If tools are unavailable".
**Rationale:** Handoff forbids fabricated build logs or false verification. Smallest missing tool to advance: an installed Unity 6.3 LTS editor (any `6000.3.x` patch) on the owner's machine; second: Android SDK/NDK or macOS+Xcode for device smoke builds.
**Status:** Approved (required honesty rule).

## 2026-10-14 — D-004 Editor/version pin policy (deviation from Blueprint §15.2 "record at M0")
**Decision:** `Packages/manifest.json` is committed with **provisional package pins** for the 6000.3 stream and `ProjectSettings/ProjectVersion.template.txt` instead of a fabricated `ProjectVersion.txt` patch number. `Tools/Build/pin_toolchain.py` stamps the real editor version once an editor is installed. The first open of the project in the chosen editor resolves packages, writes `ProjectVersion.txt` and `packages-lock.json`, which the owner commits.
**Rationale:** The blueprint forbids inventing package versions/patch numbers; this sandbox cannot query Unity's package registry (network is restricted to GitHub/npm/PyPI). Provisional pins are explicitly flagged and one command re-pins them.
**Status:** Provisional — owner must run `pin_toolchain.py` (or edit `Packages/manifest.json`) on first setup. Requirement BUILD-01 stays **Blocked** until then.

## 2026-10-14 — D-005 Input actions loaded from JSON at runtime
**Decision:** `WayfinderControls.inputactions` is committed as authored JSON and `InputRouter` builds the `InputActionAsset` via `InputActionAsset.FromJson` (Resources TextAsset). No generated C# wrapper dependency on `.meta` importer settings.
**Rationale:** Keeps input functional even before the importer generates wrapper code; avoids GUID/meta coupling in a hand-authored repo. Equivalent bindings and rebinding behaviour.
**Status:** Approved.

## 2026-10-14 — D-006 Scenes generated by editor setup script
**Decision:** Bootstrap, Title, PhysicsTestGround and VerticalSlice greybox scenes are created by `Tools → Wayfinder → Setup Project` (`Assets/Wayfinder/Scripts/Editor/SceneBuilder.cs`), which also wires URP/quality/player settings. Hand-writing `.unity` YAML with fabricated script GUIDs is rejected as fragile.
**Rationale:** Editor setup scripts are explicitly allowed by the handoff; programmatic scene building is deterministic and reviewable.
**Status:** Approved.

## 2026-10-14 — D-007 Pure domain core without UnityEngine references
**Decision:** Game rules that the blueprint requires to be unit-testable (stable hashing/PRNG, stat resolver, powertrain/fuel/damage formulas, inventory, economy ledger, transactions, missions, discovery/map, research, save envelope/atomic file protocol, chunk streaming state machine, route graph) live in code with **no UnityEngine dependency**, mirrored into `Assets/Wayfinder/Scripts/Core|Progression|Persistence|World` domain classes. UnityEngine-facing adapters (WheelCollider, Addressables, MonoBehaviours) wrap them.
**Rationale:** Blueprint §16 "explicit small services and pure testable domain logic"; enables the same logic to be exercised by NUnit EditMode tests and kept honest.
**Status:** Approved.

## 2026-10-14 — D-008 Content is data-first JSON with ScriptableObject import
**Decision:** Canonical content definitions are JSON under `Assets/Wayfinder/Content/` (auditable, generator-friendly, per §17.1 "backed by exportable JSON/CSV"). `ContentImporter` (editor) converts to ScriptableObjects and computes a catalog hash. Validators run headlessly (Python) and in-editor (C#).
**Rationale:** Enables full release-scope content (100 landmarks / 200 caches / 20 missions / 30 contracts / 20 tiers / 4 vehicles / 10 camps / 5 garages / 25 relics) to be complete, validated, and counted here.
**Status:** Approved.

## 2026-10-14 — D-009 World greybox bake approach
**Decision:** Deterministic height function (StableHash-seeded ridged/fractal noise + biome masks + authored road/river constraints) in pure C# (`Wayfinder.World`), editor `WorldBaker` bakes 256 m chunk greybox meshes/colliders and seam reports. Canonical seed `481516`, generator version `1` (§7.1).
**Rationale:** §7 hybrid pipeline; deterministic and testable without device access. Full authored dressing remains M5 content work.
**Status:** Approved (greybox = M3 scope).

## 2026-10-14 — D-010 Save JSON via Newtonsoft with canonical checksum
**Decision:** Save envelope per §17.3, payload serialized to canonical JSON (sorted keys, invariant culture) and SHA-256 checksum over canonical payload bytes. Atomic protocol: temp file → parse-verify → backup rotation → replace (`File.Replace` with same-filesystem fallback). Settings live in a separate file.
**Rationale:** §17.3/17.4 requirements; checksum detects accidental corruption; canonical form makes the checksum stable across dictionary ordering.
**Status:** Approved.

## 2026-10-14 — D-014 Headless C# verification harness with pinned provenance
**Decision:** Add `Tools/Build/headless_cs.py`, which bootstraps a real Roslyn 3.9.0 `csc` (C# 9, the Unity 6 language level) on a .NET Core 3.1.23 runtime, builds Newtonsoft.Json 13.0.3, NUnit 3.13.3/NUnitLite and a .NET Standard 2.1 reference assembly from source, and then (a) compiles every non-Unity assembly with the real `.asmdef` reference graph at `-warn:4`, (b) runs the EditMode NUnit suites, (c) recompiles the runtime assemblies against **only** the .NET Standard 2.1 reference (Unity's API profile), (d) parse-checks the Unity-dependent files. Every artifact is pinned by commit/tree hash or SHA-256 and comes only from the hosts reachable here (GitHub, PyPI). Run outputs go to `Logs/headless/` (ignored); cited results are copied under `Docs/evidence/`.
**Rationale:** D-003 forbade calling C# "Verified" without a compiler. Rather than keep guessing, obtain a real compiler within the egress policy. The harness is explicitly *not* a Unity build (KI-016) and `Implemented`→`Verified (headless)` is only claimed for assemblies that compiled, passed the profile check and executed their tests.
**Alternatives rejected:** Building Mono from source (hours, needs OpenSSL build); .NET SDK from the npm mirror (its 2.0 runtime needs `libunwind.so.8`, absent); vendoring compiler binaries into the repo (size, licensing).
**Status:** Approved. Evidence: `Docs/EVIDENCE_CS_HEADLESS.md`.

## 2026-10-14 — D-015 `SurfaceType` lives in `Wayfinder.Core`
**Decision:** The `SurfaceType` enum moved from `Wayfinder.Simulation` (`SurfaceTable.cs`) to `Wayfinder.Core` (`Core/SurfaceType.cs`). `SurfaceTable` and all consumers are unchanged apart from `using Wayfinder.Core;`.
**Rationale:** `Wayfinder.World` consumed the enum but its asmdef does not (and per ARCH-01 should not) reference `Simulation`; the headless compile exposed this as CS0246. Surface identity is a shared vocabulary term, which is what `Core` is for.
**Status:** Approved.

## 2026-10-14 — D-016 EditMode tests must not require `UnityEngine` to locate content
**Decision:** `ContentCatalogTests` resolves `Assets/Wayfinder/Content` via `UnityEngine.Application.dataPath` only under `UNITY_5_3_OR_NEWER`; otherwise via `WAYFINDER_CONTENT_DIR` or walking up from the test assembly to the repository root. Suites in `Wayfinder.Tests.EditMode` stay free of `UnityEngine` unless a test genuinely needs the engine.
**Rationale:** Keeps the EditMode suites runnable both in the Unity Test Runner and headlessly (D-014).
**Status:** Approved.

## 2026-10-14 — D-017 Save serialization uses explicit `SaveJson` settings
**Decision:** All `SaveService` serialize/deserialize/verify calls go through the `SaveJson` settings: `ReadSettings` = invariant culture, `ObjectCreationHandling.Replace`, `DateParseHandling.None`, `MissingMemberHandling.Ignore` (forward-compatible reads); `WriteSettings` = invariant culture, `DateParseHandling.None`, indented. `CanonicalJson` (checksum input) also parses with `DateParseHandling.None` so ISO timestamps are never re-formatted.
**Rationale:** Newtonsoft's default `ObjectCreationHandling.Auto` appends arrays into pre-initialised `List<T>` fields, which doubled every list on parse-verify and made the checksum fail on 100 % of saves (KI-013). Explicit settings make the save format independent of DTO field initialisers and of Newtonsoft defaults between versions.
**Status:** Approved.

## 2026-10-14 — D-018 `ResearchService` takes an injected story-gate predicate
**Decision:** `public ResearchService(Func<string, bool> isMissionCompleted = null)`; when null it falls back to `MissionService.Global`. `ResearchService.Global` keeps the fallback. The composition root may pass `MissionService.Global.IsCompletedCode` explicitly.
**Rationale:** The implicit static dependency made research tests order-dependent and hid the coupling; injection is the smallest change that keeps the no-monolith rule (ARCH-02) and makes the gate testable in isolation.
**Status:** Approved.

## 2026-10-15 — D-019 `Wayfinder.Campaign`: engine-free composition root and expedition lifecycle
**Decision:** Add `Assets/Wayfinder/Scripts/Campaign/` (`Wayfinder.Campaign.asmdef`, `noEngineReferences: true`, refs Core/Simulation/World/Progression/Persistence/Newtonsoft). `CampaignSession` owns **one instance per save slot** of every progression service (economy, inventory, discovery, missions, research, garage, contracts, transactions, clock, damage), maps them to/from `SavePayload` (`CampaignSnapshot`), and implements the §2.3 lifecycle (new game, depart, field actions, extraction, rescue). `SliceFieldController` turns per-frame vehicle telemetry into prompts/discovery/checkpoints/arrival; `HudModel`/`GarageModel`/`SummaryText` produce UI strings. MonoBehaviours (`CampaignHost`, `TitleFlowHost`, `VerticalSliceDriver`) only render and forward input. `TransactionService` receives its collaborators through `TransactionDependencies`; there is no fallback to `ResearchService.Global` any more (amends D-018; the `Global` instances remain only for legacy callers).
**Rationale:** The session needs both Progression and Persistence, must be testable headlessly (D-014) and must not become a Unity "GameManager" (ARCH-01/02). §15.3 lists folders but not this layer; a separate assembly keeps the asmdef graph acyclic (Platform/Presentation/Editor → Campaign → Persistence → Progression).
**Status:** Approved (implementation-side).

## 2026-10-15 — D-020 Snapshot persistence: commit-or-rollback critical operations, debounced field progress
**Decision:** The campaign is persisted as one snapshot. **Critical** operations — new game, depart, extraction/banking, full rescue, research, crafting, mission accept, camp establishment, camp deposit, relay activation, quest-item pickup — mutate memory, write + verify a new revision, and only then acknowledge; if the write fails, memory is restored from the pre-operation snapshot and the caller receives `FailureReason.SaveIoFailure` (HUD notices raised inside are discarded). **Field progress** (cache pickups, landmark discovery, map reveal, inspections, checkpoints, cargo moves, pose/fuel telemetry) marks the session dirty; `AutosavePolicy` saves 15 s after the first unsaved change (≥ 10 s between saves, 20 s retry after a failure, unscaled time). Suspend/quit saves immediately when dirty. `SaveService` gained a null-by-default `StepHook` test seam so interruption can be injected after every persistence step.
**Rationale:** §12.4/§16.2/§17.4 require "old or new complete state" and "never claim success". Snapshot saves make consistency structural: a crash inside the debounce window loses the pickup *and* keeps the cache uncollected, so nothing duplicates. 15 s sits inside §16.2's 10–20 s window.
**Status:** Approved.

## 2026-10-15 — D-021 Additive save fields at schema 1 + derived transaction sequence
**Decision:** `SavePayload.nextTransactionSequence` and `ExpeditionDto.stats` were added without bumping `CurrentSchemaVersion` (still 1). On load the next sequence is `max(nextTransactionSequence, highest ":<n>" suffix in appliedTransactionIds + 1)`, so payloads without the field cannot reissue an applied id. Transaction ids are `<expedition-or-hub-scope>:<global sequence>`.
**Rationale:** No public build or save exists, reads ignore unknown members and missing fields default safely; a reused id would turn a legitimate new pickup into a silent idempotent no-op (proven by `TransactionSequence_SurvivesReload_NoSilentIdCollision` and the mutation check). **Once any build ships, every further field change must bump the schema and add a migration (§17.5).**
**Status:** Approved; revisit at first public release.

## 2026-10-15 — D-022 Onboarding and recovery rules in the campaign layer
**Decision:** (a) A new game starts with **Q01 already accepted** and a `tutorial.active` flag that clears when Q01 completes. (b) Accepting a mission pre-satisfies objectives already true in the persistent world (landmark discovered, camp active, relay active, protected item held, map %) so a late accept can never dead-lock a one-time objective. (c) Full rescue = drop 25 % of loose `salvage_bundle` (rounded down) and then run the normal extraction at the nearest unlocked garage (banks the remainder and escrow, turns in ready missions, refuels/repairs); it is **free while the tutorial flag is set and in Relaxed Exploration**. (d) Mission objectives are routed by typed condition (`ReportCondition`), and `TraverseCheckpoints` only counts the next checkpoint in order.
**Rationale:** §2.3 "teaches the loop in under ten minutes", §5.6 "free in the tutorial", §1.4 "Relaxed: no reward punishment", §2.5 "missions never regress". Ordered checkpoints need no extra persisted state and cannot be inflated by re-driving a gate after a reload.
**Status:** Approved (design interpretation; owner may tune).

## 2026-10-15 — D-023 Hub settlement, storage and module simplifications for the slice
**Decision:** Items have a settlement category: Currency (`salvage_bundle`) banks 1:1; Materials (scrap/polymer/electronics/alloy) move to hub storage; Consumables (fuel can, repair kit, tire patch, boards, camp kit) and mission objects stay loaded as the loadout; protected-ledger objects never move. Garage storage is unlimited (10 000 slots / 10⁶ kg); camps share **one** 500 kg camp store (the v1 save has a single `campStorage`); materials that do not fit stay in cargo — nothing is lost. Researched modules are treated as installed (no slot-equip UI yet), which is what `ResearchService.ApplyTo` already assumed. The starting loadout is loaded into cargo.
**Rationale:** "Loose cargo is converted or stored" (§2.3) without forcing the player to re-load supplies every trip. Per-camp storage + hub-transfer UI and module slots (§10.2) are deferred (KI-028); they need a schema change.
**Status:** Provisional — revisit with the full garage UI.

## 2026-10-15 — D-024 Vertical-slice manifest and world-coordinate greybox
**Decision:** `Content/vertical_slice.json` defines the §21.3 slice: area x∈[512,1536), z∈[1792,2816) centred on `garage.home`; landmarks forest.01–06 (all *Gentle*; 01 and 06 are vistas); twelve caches (6 small / 4 standard / 2 remote, each ≥ 60 m from the garage yard and ≥ 10 m apart, chosen so the slice supplies the second camp kit's materials); Q01–Q04; tiers 1–6; two camp sockets, the creek-gauge inspect target, two ford checkpoints, the relay-fuse site, `relay.forest` and greybox features. Landmark/cache positions come from content `positionHint` (single source); the manifest authors only placements content leaves unset (camp sockets are `(0,0,0)` in `camps.json`). `SceneBuilder` generates the VerticalSlice scene in **world coordinates** from this data; `ProjectSetup` copies the campaign JSON into `Resources/Content` (git-ignored, generated). `validate_content.py` and `CampaignFieldTests` enforce scope, containment, reachability of every slice objective and affordability (income without mapping 3436 ≥ 3130 spend).
**Rationale:** One data source drives tests, validator and scene. The placeholder positions are compact (KI-027) but legal; M3 route validation may move them without changing ids.
**Status:** Approved for the greybox slice.

## 2026-10-15 — D-025 Exploration map: engine-free CPU raster, incremental redraw, texture upload
**Decision:** The map (§8.1, §13.2, §13.4) is drawn in plain C# (`Campaign/Map/`), not by a camera or shader. `ExplorationMap` owns a `MapRaster`: an RGBA32 byte array covering a window of map cells. The slice uses its 16 × 16 cells at 32 px/cell (2 m/px, 512², 1 MB); the whole 96 × 96 mainland later uses 8 px/cell (768², 2.4 MB; capped by `MapRaster.MaxTexturePixels`). Rows are bottom-up so Unity's `Texture2D.LoadRawTextureData` uploads the bytes verbatim (`Presentation/MapTextureBinding`). `Refresh()` diffs the session's revealed/surveyed `BitGrid`s against the drawn copies, 64 cells per word compare (`BitGrid.CollectDifferences`), and redraws only changed cells plus their *revealed* neighbours, which carry the soft fog edge. Fogged cells depend on nothing, so incremental and full redraws are byte-identical (tested; mutation-checked). An optional per-call cell budget spreads a vista reveal over frames; Unity uses 24 cells/frame and uploads at most every 0.25 s while cells remain queued. Fogged cells render as a blank survey sheet (parchment grain + 256 m grid). Revealed cells show surface colour × NW hillshade. Surveyed cells add 2 m contours. One `IMapTerrainSource` feeds both the map and reveal occlusion (D-028), so the map never shows relief the reveal ignored. The minimap is a `RawImage.uvRect` crop of the same texture: no second texture, no render-to-texture.
**Rationale:** Deterministic and headless-testable (pixels are asserted in NUnit and dumped to PNG evidence), cheap on mobile (no extra camera; 2 Hz reveals touch ~10–25 cells), and independent of the scene, which has no real terrain yet (KI-027/KI-029). A window keeps slice fidelity high without a 9 MB full-world texture.
**Status:** Approved (implementation-side). Device texture-upload cost unmeasured (KI-031).

## 2026-10-15 — D-026 Map spoiler policy (what the map may show)
**Decision:** (a) A new game's sheet is fully fogged. It shows only you, the home garage and the current mission's search circle. (b) **Unopened caches are never drawn**, even in revealed cells (§1 "map icons never reveal everything", §7.6); opened caches are drawn. (c) An undiscovered landmark appears as an unnamed *"Unconfirmed landmark"* ring once its cell is revealed (its silhouette has been seen); the name appears on discovery. (d) A `DiscoverLandmark` objective shows a 110 m search circle. Its centre is offset deterministically (`StableHash`) by 25–100 % of 0.45 × radius, so it always contains the landmark but never pinpoints it. (e) Mission-given sites (inspect target, the *next* ford checkpoint, camp socket, quest-item site, relay) are pinned while the objective is pending, because the briefing names the place. (f) Unlocked garages and active camps (safe hubs) are always drawn; locked garages, empty camp sockets and offline relays appear once their cell is revealed. (g) Only vertical-slice content is considered, so the map never hints at sites the scene lacks. (h) The tracked marker is the HUD's tracked objective (`ObjectiveText.TrackedLine` rule); a mission ready to turn in tracks its garage.
**Rationale:** The blueprint wants discovery to feel earned while missions stay readable (§2.3 onboarding under ten minutes). Search circles follow §8.3 "search areas" without the precise sensor rings (not in scope yet).
**Status:** Approved (design interpretation; owner may tune radius/offset).

## 2026-10-15 — D-027 Custom map markers: additive save fields at schema 1
**Decision:** `WorldStateDto` gains `customMarkers` (`MapMarkerDto` id/x/z/label, placement order), `nextCustomMarkerIndex` and `routeTargetMarkerId`, still at `CurrentSchemaVersion` 1 under D-021. `MapMarkerService` (Progression) allows **at most ten** markers (§13.4); the 11th returns `OverCapacity`. Ids are `marker.N`, and N is never reused within a save. Labels are trimmed, stripped of control characters and capped at 24 characters; empty labels default to "Waypoint N". Restore is tolerant: it drops malformed, duplicate and out-of-bounds entries and anything past ten, and lifts the next index above every surviving id. Placing, removing and routing are **field progress** (debounced autosave, D-020), not critical saves; they work in the garage and while the map pauses an expedition. Rescue never touches markers or revealed cells (§8.1).
**Rationale:** Markers are player annotations with no economic value. Stable ids keep a replayed command from retargeting another marker. Additive fields are safe because no build has shipped. **Bump the schema with any change after first release (§17.5).**
**Status:** Approved.

## 2026-10-15 — D-028 Reveal line-of-sight parameters, surveyed-flag fix, 2 Hz cadence
**Decision:** `World/TerrainLineOfSight` implements §8.1's "cheap terrain line-of-sight samples to avoid revealing behind major ridges", with these parameters:
- eye height 2 m (6 m from a vista viewpoint); target height 2 m;
- a cell is hidden only if terrain rises **> 4 m** above the sight line ("major ridge");
- samples every 16 m, at most 32;
- cells within 48 m are always revealed (the cell under the car can never stay fogged);
- unknown heights (NaN) never occlude.

The reveal path is `DiscoveryService.RevealVisibleAround`, called by `CampaignSession.RevealAround` for drive and vista reveals; heights come from `CampaignSession.MapTerrain` (the slice greybox profile, KI-029). **Fix:** vista *surveyed* flags now obey the same filter; before, a cell behind a ridge could be "surveyed" without being revealed. `SliceFieldController.RevealIntervalSeconds` changes from 1 s to **0.5 s** (§16.2 "map reveal 2 Hz"); the ≥ 16 m travel gate is unchanged, so a parked car does no work.
**Rationale:** The 4 m tolerance stops bumps and props from punching holes in the map. The slice's 8 m hill already hides part of its far side from Firewatch Nine. Reveals happen every 0.5 s **or** 16 m of travel, whichever comes later. At slice speeds the 16 m gate dominates (≈ 1.2 s at 50 km/h), and the 2 Hz cap only binds above ≈ 115 km/h. Either way the frontier stays far inside the 96 m radius.
**Status:** Approved; retune the tolerance with the baked M3 heightfield.

## 2026-10-15 — D-029 Field supplies and selling in the campaign session
**Decision:** `CampaignSession.Supplies` exposes the §5.5/§5.6/§10.3/§10.4 rules.
- **Fuel can:** usable only during an expedition, with ≥ 1 L missing. It adds `min(6, capacity − fuel)`. If any of the can would be wasted, the caller must confirm (`acceptWaste`); otherwise the result is `Cancelled` and nothing changes. The UI arms on the first tap and uses on the second. A partly used can still costs one item.
- **Repair kit:** +35 to one chosen subsystem, only while stopped (≤ 1 km/h) and out of water. It refuses a subsystem at 100, so a kit is never wasted. An engine repair ends a water-stall incident.
- **Tire patch:** v1 models a puncture as the tire-condition band < 30 (`DamageModel.PunctureThreshold`, already what `VehicleController` used). A patch lifts tires to 30: the 25 km/h cap goes, but the below-50 grip penalty stays until a free garage repair. No new save state is needed.
- Every successful use is one idempotent `UseItem` transaction. `TransactionService` consumes exactly one consumable and rejects non-consumables. Supply use is field progress (debounced autosave, D-020).
- **Selling:** only at a garage, one source at a time (garage storage or loaded cargo), 40 % of purchase price rounded down per unit. It never sells Salvage bundles (they bank 1:1), protected-ledger objects or mission cargo. It keeps as many camp kits as pending `EstablishCamp` objectives need, so Q03's free kit cannot be sold out from under the mission. A sale changes banked Salvage, so it is a **critical** operation (verified save, rollback on write failure). The garage UI asks for a confirming second tap.

**Rationale:** These follow the blueprint rules directly. Refusing wasteful uses and requiring a confirmation protect players from irreversible mistakes (§13 error states).
**Status:** Approved (implementation-side); the puncture band is a v1 simplification.

## 2026-10-15 — D-030 Researched stats reach the physics rig (KI-025 partial) and two composition fixes (KI-032)
**Decision:**
- `CampaignSession.ConfigureResolver(VehicleStatsResolver)` clears a resolver and applies exactly the researched modules, so repeated calls cannot double-apply (QA case 8). `ResolveStats()` (garage display) uses it.
- `VehicleController` exposes its own resolver (`StatsResolver`). `VerticalSliceDriver.ApplySessionToVehicle` configures it after load, research, extraction and supply use. From then on every stat the rig resolves includes research: wading depth, fuel drain, tank capacity, grip baseline, torque.
- The rig clamps fuel to the **resolved** capacity, so the driver no longer widens `spec.FuelCapacityLiters` at runtime.
- Two defects found while wiring this are fixed (KI-032): `VehicleStatsResolver.GripFor` now composes Trail Tires I (`DirtGravelGrip` ×1.10) on packed dirt/gravel for the all-terrain set only (§11.1 tier 1 + note), and `Powertrain` scales the torque curve by `stats.PeakTorqueNm / spec.PeakTorqueNm` (Engine Tune).
- **Deferred to M1 calibration:** WheelCollider friction still uses the resolver's packed-dirt baseline for all four wheels; per-wheel surface grip only scales braking. In physics the Trail Tires bonus therefore applies on every surface; the garage display is exact. Suspension travel/clearance research is not yet applied to WheelCollider geometry.

**Rationale:** One authoritative resolver configuration for display and driving (§11.2). Per-surface friction changes vehicle feel and interacts with the mud traction model, so it needs in-editor tuning, not blind edits.
**Status:** Approved; KI-025 stays open for the calibration items.

## 2026-10-15 — D-031 Input System repinned 1.12.0 → 1.20.1 (the cloud build's only error)
**Decision:** `Packages/manifest.json` pins `com.unity.inputsystem` **1.20.1**. The blueprint's 1.12.0 pin cannot compile on Unity 6000.3.26f1: its `InputSystem/Editor/InputSystemPluginControl.cs(47,25)` references `BuildTarget.ReservedCFE`, an enum member Unity 6000.3 removed, so every cloud build aborted with `error CS0117` (run 38754979851, `Docs/evidence/cloud-build-2026-10-15/`). Verified against the upstream package source (`Unity-Technologies/InputSystem`): the reference is replaced by the literal `(BuildTarget)49` from **1.13.1** onwards. 1.20.1 (2026-10-05) is the newest 1.x and the first whose `package.json` declares `"unity": "6000.0"`, i.e. built for the Unity 6 stream this editor belongs to. Fallback ladder if a run disproves it: **1.16.0** (first release with an explicit "fixed warnings on Unity 6.3" entry) → 1.14.2 → 1.13.1. Never 1.12.0 or 1.13.0.

## 2026-10-16 — D-034 Scatter spacing and streaming hysteresis (M3, Batch G)

**Decision:**
- **Scatter (§7.6):** the world is tiled by a candidate grid whose cells tile each 256 m chunk exactly. Cell size is `256 / floor(256 / spacing)`, which is ≥ the minimum spacing, so each candidate is owned by one chunk and confined to its cell. Each candidate's randomness is `StableHash.CandidateSeed(ChunkSeed(owner chunk, layer), globalIndex)` (§7.3). A candidate is accepted when it is eligible (density draw, height band, slope, road-edge clearance, not reserved) and no eligible candidate within the spacing has a higher `(priority, index)`. Two accepted points are therefore never closer than the spacing, and neighbouring chunks agree at their borders because each candidate is computed from its global index alone. Trees use a 1 m road clearance; other species set their own.
- **Activation (§18.3):** the 3 × 3 ring around the player's chunk is always instantiated. Outside it, a chunk is instantiated when its rectangle is within **256 m** of the player and kept until **384 m**. Distances are measured from the player to the chunk rectangle, not in chunk indices. This is the metre-based "unload farther than the load threshold" rule in §18.3, extended to instantiation.
- **Data retention:** a chunk that leaves the activation band but stays within **640 m** is deactivated and keeps its data (`Deactivating → DataReady`, a new legal transition in `ChunkStateMachine`). It is unloaded only beyond 640 m.
- **Worst cases (asserted by tests):** instantiated ≤ 4 × 4 during a crossing, retained data ≤ 6 × 6.

**Rationale:** Chunk-index hysteresis was tested first and failed. A one-chunk move shifts the whole keep window, so oscillating across a boundary deactivated about three chunks per crossing (1218 deactivations in 400 crossings). Metre bands measured from the player do not move when the player jitters across a border. Dormant retention keeps re-entry free of IO. The 4 × 4 instantiated worst case is a deliberate trade against the 3 × 3 wording in §18.3: the 3 × 3 ring is still always active, and the extra column exists only while the player is crossing or retreating.

**Status:** Approved (implementation-side). Measured on the analytic test surface only. The 4 × 4 instantiated bound is an owner-review item, to be confirmed on device against the frame budget (KI-038, KI-037).

## 2026-10-19 — D-036 Fetch Unity's log past gh's escape-sequence guard, and treat absence as evidence

**Decision:**
- **Download through a chain, then sanitise whatever arrives.** `fetch_job_log.sh` tries `curl`
  first (it writes bytes verbatim, follows the API's 302 to the signed log URL, and is immune to
  gh's guard), then `gh api … --allow-escape-sequences`, then plain `gh api` for versions too old
  to know the flag. gh ≥ 2.63 refuses a raw non-JSON body carrying terminal escape sequences — and
  redirecting stdout does **not** bypass the guard (`!isJSON && !opts.AllowEscapeSequences &&
  bodyWriter != io.Discard`, `pkg/cmd/api/api.go`). The chain is PR #15's; the half it was missing
  is that **verbatim is not parsable** (next bullet), so the two are complementary rather than
  alternative fixes and were merged rather than chosen between.
- **The saved log is sanitised plain text.** CSI/OSC sequences, lone `ESC` and `\r` are stripped
  before anything parses the file: they split the exact lines the reporter greps for
  (`error CS0117:`, `Aborting batchmode due to failure:`) and GitHub's workflow-command parser
  rejects `ESC` in annotation text. The intermediate-byte class is `[ -/]` (space..slash), never
  `[ -\/]` — a backslash is not an escape inside a POSIX bracket expression, so `[ -\/]` means
  space..backslash and ate real log text (`ESC[KAborting…` → `orting…`).
- **Report what sanitising removed, and keep the tail.** The byte delta is printed, so a sanitiser
  that ever eats content is visible; a 400-line/400-char `.excerpt` rides up in
  `Wayfinder-APK-error-logs`, because annotations carry a few hundred characters and the cause of a
  hard stop is the last thing Unity said. The verbatim download stays in a temp file: a failing
  Unity job log runs to tens of MB and uploading it twice buys nothing.
- **A killed editor is a named cause.** New reporter patterns for `Crash!!!`, native stacktraces,
  `Fatal Error!`, OOM-killer/`Killed process`/cgroup-OOM, fatal signals, core dumps and
  `No space left on device` — deliberately narrow, because Unity also logs benign
  `Received signal SIGUSR1` and "out of memory" retry lines that must not be mistaken for a cause.
- **Absence is evidence.** `EditorFailureLog` writes `Logs/wayfinder-editor-failure.log` before an
  entry point rethrows, so when a Unity step failed and that file does not exist, the reporter now
  says so: no C# exception was thrown inside the build method, so the cause is earlier (compile
  error, package resolution, licence, unresolvable `-executeMethod`) or the process was killed.
  This is stated only where Unity actually ran (a `Logs/` directory exists) — never in the diagnose
  job's fresh checkout, where it would be a statement about nothing.
- **The refusal notice names a cause, not a scapegoat.** Its advice is now derived from the error
  text: an escape-sequence refusal says to check the runner's `gh` version, a real
  403/404/scope error mentions `actions: read`, and anything else points at the Actions tab. The
  old blanket "Needs `actions: read`" is what sent three investigations after a permission the
  workflow had already granted.
- **Do not warm the `Library` cache yet.** `actions/cache@55cc834` declares `post-if: "success()"`,
  so no `Library` cache can be saved until a run succeeds (KI-042). Saving one from a *failed*
  import via `actions/cache/save` + `if: always()` was considered and rejected: it would introduce
  an uncontrolled variable into a diagnosis that is not finished. Revisit after the first success.

**Rationale:** runs 39139527909, 39141218150 and 39141401948 each failed identically and each
diagnose job printed the same refusal twelve times. D-035 built the right mechanism and its tests
stubbed a permissive `gh`, so the guard was invisible from this environment — the notice even
misattributed the failure to a missing `actions: read` that was already granted, sending three
investigations after a non-problem. The refusal text is the evidence; gh's source confirms the
mechanism; a dress rehearsal reproduces it with the base-commit fetcher and shows the current one
annotating a compile error from the same stub.

**Status:** Approved; executed locally only. 91/91 diagnostics tests, 23/23 pipeline tests, 19/19
mutations caught for this batch and 22/22 for Batch H, dress rehearsal green over both download
paths (`Docs/evidence/cloud-build-2026-10-19/`). **No part of it has run in CI.** The Unity root

## D-037 — How the DEF-001…DEF-025 defects were closed (2026-10-19)

**Decision.** Every defect in `Docs/AI_BUG_REPORT.md` is fixed in code and pinned by a test. Six
design choices had to be made where the report left the fix open, and they are recorded here
because content and save compatibility are involved:

1. **A garage unlocks when the player reaches it (DEF-003).** `UnlockGarage` is a real command,
   executed by `TransactionService` inside `Extract()` before the "is it unlocked?" check. Free
   (§11.4 — garages never charge). Rationale: Q05's objective is `VisitVolume(garage.canyon)`, and
   `VisitVolume` is reported only by a successful extraction, so *any* rule that requires the garage
   to be unlocked first deadlocks the chain. Reaching a place to open it is also the only rule that
   needs no new currency sink.
2. **The 23 mission sites no catalog defined are authored in `Content/sites.json` (DEF-003).**
   `relay.*` uses the §6.1 region relay anchors from `WorldConstants` — `"provenance":
   "spec-anchor"`. The other 19 are placed by `Tools/Content/author_missing_sites.py` on a
   golden-angle spiral around their biome anchor — `"provenance": "procedural"`. They are editable
   data, not level design; the generator is deterministic so regenerating is safe.
3. **`document.pump_diagram` is a real item (DEF-003).** Q14 collects it, but it existed in neither
   `items.json` nor `ItemCatalog`, so the objective could never complete. Added to both (1 unit,
   1 kg, not sellable).
4. **Contract rewards are escrowed, not granted (DEF-007).** `CompleteContract` claims the reward
   key through `ClaimedRewardLedger` and calls `Economy.Escrow`, so payment is exactly-once and is
   banked with the next extraction like every other pending reward. The old
   `ContractService.Complete(...)` direct-grant path is kept for the tests that pin it, marked as
   legacy, and is not used by gameplay.
5. **Escrow is keyed by hub (DEF-017).** `Economy.Escrow(amount, hubId)` plus
   `BankEscrow(hubId)`: a bank releases the unattributed pool and that hub's own share, never
   another hub's. Rewards earned in the field (mapping, landmarks, contracts) stay unattributed on
   purpose, so they remain bankable at any hub — the reported symptom was a *hub-tagged* reward
   being swept by an unrelated bank, and this keeps banking convenient while fixing that.
   `wallet.escrowByHub` is additive, so an older save loads with everything unattributed.
6. **The countable mask is baked deterministically and persisted (DEF-008).** Measured first: the
   mainland macro heightfield spans 131–415 m, so **no** map cell is below sea level and the
   land-only rule leaves all 9,216 cells countable — the "counts ocean" symptom is not reproducible
   in this world. What was really broken is that the mask was written as `""` on every save and
   `WorldBaker` had no way to install a refined one. Both are fixed (`SetCountableMask`, and the
   mask now round-trips); the bake is correct and future-proof if the world gains water.

**Rationale.** The report's own fix column offered "implement X **or** scope it out" for several of
these. Scoping out 16 of 20 missions would have made `IMPLEMENTATION_STATUS.md` honest by making
the game smaller; authoring the missing sites makes it honest by making the content exist, which is
what the mission table already assumed. Where a value had to be invented (site positions), it is
marked in the data and generated by a checked-in script rather than typed by hand.

**Status:** Executed locally. 188/188 EditMode tests, `validate_content.py` clean,

## 2026-10-21 — D-039 Safe-hub travel: the hub you are at, the hubs you may reach, and what a camp may not offer

**Decision.** §10.4 hub travel is implemented in the domain, not in UI, and it is data-driven end to end.

1. **"Where am I?" is a domain query.** `CampaignSession.CurrentHubId` returns the parked hub
   (`Expedition.LastGarageId`) when not on expedition; otherwise the nearest **activated** camp whose
   socket satisfies `pose.DistanceXZ(socket.Position) <= socket.RadiusMeters`; otherwise null. Null is
   the open field, and the open field offers no fast travel — that is what full rescue is for (§5.6).
2. **The gate is content, not code.** `garages.json services` and `camps.json functions` are now parsed
   into `GarageDefinition.Services` / `CampDefinition.Functions`, and `CampaignContent.OffersHubTravel(hubId)`
   checks the `hubTravel` key (`CampaignContent.HubTravelService`). All five garages and all ten camps
   declare it in the shipped content — a test asserts that — so a hub can be *authored* out of the
   network without a code change. Activation still gates through `GarageService.TryHubTravel`, so an
   unestablished camp or a locked garage is not a destination.
3. **Refusal order is part of the contract.** Empty destination → `InvalidTarget`; no current hub →
   `WrongState`; `inWater || inDeepMud` → `WrongState` ("no fast travel out of a dangerous field
   situation; use full rescue"); destination == origin → `WrongState`; activation gate; content service
   → `InvalidTarget`. The danger parameters are **required**, not defaulted, so no call site can skip
   the check by omission.
4. **Free, instant, and committed like any critical operation.** No currency fee and no loading-screen
   punishment (§10.4). The move runs inside `RunCritical`: pose **and** safe pose are re-based, the
   `HubTravelled` notice is emitted, and a failed verified save rolls the whole move back with a typed
   `SaveIoFailure`.
5. **Fast travel never moves the extraction target.** `Expedition.LastGarageId` is re-based only when
   the session is parked; mid-expedition it stays put, so banking/rescue still resolve to the garage the
   expedition departed from (§12.4). Teleports also cannot inflate `Stats.DistanceMeters`:
   `UpdateVehicle`'s `MaxPlausibleStepMeters = 50 m` already treats a large jump as a reset.
6. **`AtGarage` ≠ `InGarage`.** `InGarage` means "parked, not on expedition"; the new `AtGarage` means
   "parked **at a garage**" (`InGarage && Content.Garages.ContainsKey(LastGarageId)`). The six
   garage-only services — mission board, research, contracts, loadout moves, crafting, selling — now gate
   on `AtGarage`, so a camp offers exactly §10.4's camp functions (save, deposit, fuel, repair supplies,
   time of day, map, hub travel) and nothing permanent.
7. **`SpawnFor(hubId)` resolves camp sockets.** It was garage-only and silently fell back to the home
   garage position for any unknown id — a latent bug that hub travel would have turned into "depart from
   the wrong place". It now returns the authored slice-garage spawn, another garage's position, or an
   activated camp's socket position, in that order.

**Rationale.** Every rule above is a sentence in §10.4 or §12.4; the only inventions are the refusal
*order* (which makes the danger check impossible to bypass and the messages diagnosable) and the
`AtGarage`/`InGarage` split. The split is the smallest change that makes a camp a hub without making it
a garage: for every save that predates hub travel `LastGarageId` was always a garage, so
`AtGarage == InGarage` and existing behaviour is bit-for-bit unchanged — a test pins that equality.
Making the service list data-driven keeps §10.4's "hub travel is a service a hub offers" literal, and
mutating the real catalog in a test (rather than mirroring the rule in a test double) is what makes the
gate falsifiable: a mutant that drops `OffersHubTravel` from `TravelToHub` is caught.

**Status:** Executed 2026-10-21. 15 `CampaignHubTravelTests`, 15/15 mutation checks caught, suite
216/216 with 0 warnings. UI for hub travel remains Unity-side work (KI-026).

## 2026-10-21 — D-040 Per-camp storage: schema 2 and the first executed save migration

**Decision.** Camp storage is per-camp, and the change is carried by a real schema bump rather than an
additive field.

1. **One container per camp.** `CampaignSession.CampStorageFor(campId)` (`"campStorage:" + campId`)
   replaces the static pooled `CampaignSession.CampStorage`. Each store is configured with
   `CampStorageSlots` and **that camp's own** `camps.json storageCapacityKg`, falling back to
   `CampService.CampStorageCapacityKg` (500 kg) only for content that omits it. Configuration runs on
   load, on `EstablishCamp` (so a new camp's store exists without a reload) and defensively before a
   deposit; it is idempotent.
2. **Schema 2, not another additive field.** D-021/D-027 established that a *purely additive* field
   needs no bump. This is not additive: the meaning of `campStorage` changes — a single pooled store
   becomes N stores — and existing data must be *moved*, which is precisely what §17.5 migrations are
   for. `SavePayload` gains `campStores` (`CampStoreDto` = campId + items); `campStorage` stays so a v1
   file still deserializes, and this build never writes to it again.
3. **`SaveMigrations.Steps[1]` is the project's first executed step.** Pooled rows merge by
   (itemId, missionInstanceId) into the store of the **first camp in `activatedCampIds`** (capture sorts
   that list, so the choice is deterministic), or into `garageStorage` when the player never established
   a camp. Rows that carry nothing — null, empty id, quantity ≤ 0 — are dropped; every real unit
   survives. The pooled field is emptied so the step cannot double-apply, and the envelope's
   `payloadChecksum` is recomputed, because the checksum covers the payload and a migrated envelope must
   stay self-consistent for any later verify (§17.4).
4. **The `Migration` delegate is typed on `SavePayload`, not `JObject`.** The scaffolding's comment
   suggested JObject transforms, and the first implementation did exactly that — and **silently lost the
   migrated store**: re-assigning an already-parented `JArray` back onto the `JObject` that owned it
   detached it, so the step emptied `campStorage` and produced no `campStores` entry, with no exception
   anywhere. A typed step mutates the DTO graph the envelope already carries; there is no serialization
   boundary left to lose a field in. This is the reason the delegate signature changed.
5. **Restore is belt and braces.** Capture writes one store per activated camp in sorted order (so
   "save → load → capture" stays byte-identical) and never writes the pooled field. Restore rebuilds
   each camp's container from `campStores` *and* adopts pooled rows from any payload that still carries
   them — into the first activated camp, else garage storage — so a hand-edited or unmigrated file
   cannot lose property either (§17.5).

**Rationale.** "One shared 500 kg camp store" made camps interchangeable warehouses and contradicted
§12.2's per-site logistics; per-camp stores also give the capacity field in `camps.json` a meaning.
Bumping the schema costs one migration and buys an executed, tested migration path — until now
`SaveMigrations` had never run in any build, so M7's "save migrations from public versions" had no
evidence at all. The silent-loss bug is the argument for typing the delegate: a JSON-level transform
failed *quietly* in the one place whose whole job is not losing player data, and only a test that
round-tripped through disk caught it.

**Status:** Executed 2026-10-21. 9 `CampaignCampStorageTests` (including two on-disk schema-1
migrations and pooled-row adoption) + 4 migration tests in `PersistenceTests`; 12/12 mutation checks
caught; suite 216/216, 0 warnings; `validate_content.py` and `formula_checks.py` clean.


## 2026-10-21 — D-041 §10.2 equipment slots: the fitted loadout composes, and unlocks come from research

**Context.** The last open half of KI-028. §10.2 gives the Scout one module per named slot — tire set,
suspension package, engine tune, tank package, intake package, differential package, cargo rack,
sensor, winch — plus **two utility slots**, and states that permanent modules never compete with
consumable cargo. Until now `ResearchService.ApplyTo` composed *every* researched tier: buying
Suspension II stacked its travel on Suspension I's, three cargo racks summed their slots, and the two
utility tiers were indistinguishable from the named ones. `Stat.RockTires` existed in the resolver and
**nothing in content or code ever set it**, so the Rock tire set — which §10.2 prices at +20% dry rock
grip — was unreachable in every save.

**Decisions.**

1. **A slot is a property of the tier table, and content mirrors it.** `ModuleSlot` lives in
   `Wayfinder.Progression` beside the 20 tiers; `upgrades.json` carries the same slot per tier as
   `moduleSlot`. The spellings come from `Wayfinder.Simulation.EquipmentSlots` — the §10.2 vocabulary
   the resolver already published and nothing consumed — so the enum, the JSON, `validate_content.py`
   and `ContentCatalogTests` cannot drift apart on names. `ResearchService.SlotName` /
   `TryParseSlot` are the single authority for the string form. Utility is one slot *kind* with two
   instances, spelled `"utility"` rather than `Utility1`/`Utility2`: a module does not choose which of
   the two it occupies. `"none"` is not a slot — it marks a research unlock.
2. **Only what is fitted composes.** `ApplyTo` skips a researched tier that occupies a slot and is not
   in the fitted set. Slot-less tiers (8 Mud Tires, 18 Cold-Weather Kit) are unlocks rather than
   equipment: being researched is enough, and they always compose.
3. **Researching a module fits it.** The tree is strictly progressive, so the newest module in a slot
   is the sane default — and this preserves the meaning of all 216 existing tests, which buy tiers and
   assert their effects. The player may still fit an earlier module, or none: dropping the Expedition
   Rack's loaded-COM penalty or the diff lock's turning scrub is precisely the "meaningful terrain
   preparation" §10.2 asks for. A full Utility slot leaves the new module unfitted instead of failing
   the purchase — the Salvage was spent and the research is permanent (§17.5).
4. **Fitting a named slot replaces its occupant; Utility refuses a third.** One module per named slot
   is §10.2's rule, so replacement is the only legal move and needs no confirmation step. The
   third-utility refusal is defensive: canonical content has exactly two utility tiers and fitting an
   already-fitted module is refused earlier as `AlreadyApplied`, so that branch is unreachable through
   the public API. It is recorded here as uncovered rather than claimed as tested.
5. **Tire-set unlocks come from research, not from the fitted loadout.** `IsTireSetUnlocked` scans
   researched tiers for the `MudTires` / `RockTires` / `SnowTires` flag, so removing the differential
   lock never un-unlocks the Rock set. §11.2 tier 13 now sets `RockTires`, closing the unreachable-set
   defect, and tier 20 carries `PeakTorqueNm ×1.10` forward from tier 10: §11.2:739 asks for
   "explicit final stat composition", and the capstone takes the engine slot, so without the carried
   effect it would have silently dropped the torque curve while keeping only the drain change.
6. **Loadout changes are a garage service, and they are critical.** `EquipModule` / `UnequipModule` /
   `SelectTireSet` refuse outside a garage (`WrongState`; §10.4 lists "vehicle change" among the
   garage-only services), run inside `RunCritical`, re-run `ConfigureContainers()`, clamp `FuelLiters`
   to the new capacity (§5.4 — garages refuel for free, so clamping down costs the player nothing),
   and only then enforce **QA case 9**: if the loaded cargo no longer fits, the command returns
   `OverCapacity` and the verified snapshot rollback restores the previous loadout. Checking *after*
   the swap is what makes the guard exact — it tests the real composed container sizes rather than a
   prediction of them.
7. **`ResolveStats` uses the mounted set and research-derived unlock flags.** It passed
   `TireSet.AllTerrain, …, false, false, false` before, so the garage could never show a mounted
   specialized set even though §11.2:741 requires garage display == driving. `VerticalSliceDriver`
   now also assigns `vehicle.tireSet = _session.SelectedTireSet`, which nothing did before, so the
   physics rig's own `GripFor` lookup finally sees the player's choice (part of KI-025).
8. **Persistence is additive — no schema bump.** `VehicleDto.equippedTireSet` defaults to
   `"AllTerrain"`, so a schema-2 file without the field loads unchanged (the D-021 precedent; a second
   migration in one week for a field whose absence has exactly one legal meaning would buy nothing).
   `equippedModuleIds` now records the *fitted* loadout instead of every researched tier, and
   `unlockedTireSets` is written from research instead of a hardcoded `{"AllTerrain"}`.
9. **A pre-slot save reconciles to the highest tier per slot.** `Restore(researched, fitted, tireSet)`
   reads a null fitted list as "everything researched" — what an older build wrote — then walks the
   tiers ascending so the highest tier wins each named slot and the first two win Utility. For every
   canonical tier that reproduces exactly the composition the old rank-based `Set`/`Multiply` stacking
   produced, so an existing player's vehicle does not change underneath them, and no research is lost
   (§17.5). A saved tire set that is not unlocked is clamped to all-terrain rather than rejected: a
   load must not fail because content moved.

**Rationale.** Composing only what is fitted is what makes §10.2's slots mean anything: without it a
player who owns every tier drives a vehicle no tier table describes, and the rack, tank and suspension
numbers shown in the garage are fiction. Auto-fitting on purchase is the compatibility choice — it
keeps 216 existing tests asserting what they always asserted — while `UnequipModule` keeps the choice
real and reversible. Deriving unlocks from research rather than from the loadout protects a capability
the player paid for from being lost by rearranging equipment, which §17.5 forbids. The QA-9 guard sits
after the swap because `RunCritical`'s rollback is already proven, so an after-the-fact capacity check
cannot be wrong about which container sizes are in force.

**Status:** Executed 2026-10-21. 22 new `CampaignModuleSlotTests` + `UpgradeTable_MatchesCanonicalSlotsAndEffects_D041`
in `ContentCatalogTests`; suite 216 → 239 passing, 0 warnings; 27/27 mutation checks caught
(`Docs/evidence/module-slots-2026-10-21/`); `validate_content.py` and `formula_checks.py` clean.

## 2026-10-21 — D-042 §10.4 community logistics: one transfer command, gated on hub activation

**Context.** §10.4:694 — "Items stored in any camp are part of a shared logistics inventory *only
after* a safe-hub transfer action, not magically accessible for field repairs. For implementation
simplicity, version 1 allows free instant transfer among activated hubs while the player is at a hub;
no field access. Explain this as community logistics." Batch J delivered hub travel and per-camp
storage, and `GarageService` already carried the at-a-hub half of this rule
(`TryLogisticsTransfer(currentHubId)`) — but nothing called it. A player could leave 500 kg at
`camp.forest.a` and recover it only by driving back, so the shared-logistics half of §10.4 was simply
absent. This was KI-028's last open piece.

**Decision.** Two campaign commands over one shared implementation, reusing the progression gate
rather than inventing a second vocabulary for "am I at a hub".

1. **`HubStore(hubId)` is the single source of truth for where a hub keeps property.** Every unlocked
   garage resolves to the ONE unlimited `GarageStorage` container (§10.4: garage material storage is
   unlimited), every activated camp to its own `CampStorageFor(campId)` (D-039), and anything else to
   `null`. `TransferToHub` and `TransferFromHub` are one-line wrappers over a single
   `TransferBetweenHubs(from, to, …)`, so send and pull cannot drift apart — direction is the only
   difference, and mutation L9 (reversing it) is caught by two tests.
2. **The gate is hub *activation*, not a content service.** Hub travel requires the destination's
   content to declare `hubTravel` (D-039) because it moves the *vehicle* through the world. Logistics
   moves *property*, and §10.4 conditions it on nothing beyond "activated hubs while the player is at
   a hub". `camps.json` declares no `storage` function for any camp, so a service-flag gate here
   would have silently disabled camp logistics for all ten camps: the rule would have read as
   implemented while no camp could take part.
3. **`GarageService.TryLogisticsTransfer` is called, not reimplemented.** The no-field-access rule
   lives in the progression service beside `TryHubTravel`; the session asks it and returns its
   refusal verbatim, so one definition of "at a hub" governs travel, logistics and — through
   `AtGarage` — the garage-only services.
4. **Garage-to-garage is refused, not silently accepted.** Both garages resolve to the same store, so
   a "successful" transfer would move nothing yet still emit a notice and write a verified save: a lie
   in the UI and in the event log. The refusal explains itself — "every garage shares one unlimited
   store (§10.4), so there is nothing to move between two garages". A transfer to the hub the player
   is *already at* is refused earlier with its own detail ("already at that hub"), because that
   garage wording would be wrong for a camp. Both are `WrongState`, so the tests assert the detail and
   not only the reason — which is the only thing that makes mutation L4 detectable.
5. **One activation guard, placed where it is used.** The first draft checked `HubStore(other) ==
   null` and then re-checked the resolved `from`/`to`. Mutation L5 survived that draft, proving the
   earlier check unreachable in every case: `other` is always one of the two hub ids, and the at-hub
   gate has already proven `here` resolves. The duplicate is gone and the surviving guard sits
   immediately before the `from.Value`/`to.Value` dereference it protects.
6. **Free, instant, critical.** No fee, no clock advance, no distance or travel time — §10.4's
   version-1 simplification, phrased in the notice as community logistics rather than implying the
   property teleports. The move runs inside `RunCritical`, so it is acknowledged only with a verified
   save and rolls back completely otherwise (§12.4, §17.4); mutation L14 (dropping the rollback) is
   caught by this batch's test and by two pre-existing ones.
7. **Refusal order:** unknown item → protected ledger object → non-positive quantity → not at a hub →
   no hub selected → already at that hub → hub not activated → same store → transaction. Cheap,
   content-free checks first, then the positional gate, then target validity, then the move.
8. **The garage panel reads the domain instead of recomputing.** `GarageModel` gains `CurrentHubId`
   plus one `LogisticsRow` per activated hub carrying used slots, mass, capacity and stacks, with
   `SharedStore` marking garage rows and `CanExchange` false for the hub you are standing at and for a
   second garage while parked. §10.4's "show capacity" is a view concern; the numbers already live in
   `InventoryService.CapacityOf`, so `DisplayNames` gained `Camp`/`Hub` and a row reads "Forest A
   Camp" instead of `camp.forest.a`.
9. **The two defensive `ConfigureCampStore` calls are declared untested.** `ConfigureContainers()`
   already sizes every activated camp's store on load and on establishment, so removing them changes
   no observable behaviour and no mutant can catch them. They stay as belt-and-braces — a transfer
   must not depend on which command configured a container last — and are recorded here rather than
   claimed as covered.

**Rationale.** Reusing `TryLogisticsTransfer` stops §10.4's "no field access" from becoming a second,
divergent rule: the day a rescue or a hazard changes what counts as being at a hub, travel and
logistics change together. Gating on activation rather than on a content service is the smaller
invention — it needs no content edits and cannot be defeated by a camp that forgot a flag. Refusing
the two no-op transfers instead of reporting success matters because every transfer is a critical
save, and a command that writes a save, emits a notice and moves nothing teaches the player that the
log says things that did not happen. The duplicate guard's removal is the point of running mutants at
all: a survivor is a claim that some code is load-bearing, and here that claim was false.

**Status:** Executed 2026-10-21. 15 new `CampaignLogisticsTransferTests`; suite 239 → 254 passing,
0 warnings; 18/18 mutation checks caught (`Docs/evidence/hub-logistics-2026-10-21/`);
`validate_content.py` and `formula_checks.py` clean. §10.4's automated arbitrage test ("crafting and
reselling must never create currency") is still unwritten — it is a pricing rule rather than a
logistics one, and stays open on its own.

## 2026-10-21 — D-043 §10.4's arbitrage rule: three checks were weaker than the sentence, and they checked tables the runtime never loads

**Context.** §10.4:698 — "Materials can be sold at 40% of purchase price, rounded down. Crafted
consumables sell for less than their total input purchase value. Add an automated arbitrage test;
crafting/reselling must never create currency." The requested test already existed in **three** places,
and reading all three against the sentence turned up two separate problems.

*Problem 1 — every check was weaker than the spec.* `CraftingService.CraftResaleCreatesCurrency` (the
QA-17 predicate), `validate_content.py`'s `check_items_recipes` and `economy_sim.py`'s `arbitrage_scan`
each **added `salvageFee` to the input side** before comparing. §10.4's sentence counts *materials
only*; the fee belongs to QA case 17, a different rule. A recipe selling for more than its materials
but less than materials + fee would have satisfied all three checks while breaking the rule as written.
Today's four recipes clear both bars comfortably (repair_kit 18 < 32, tire_patch 8 < 12,
recovery_boards 14 < 34, camp_kit 40 < 89), so this was a latent hole rather than a live defect — but
nothing would have noticed if content moved into it.

*Problem 2 — the checks read files the runtime never loads.* `ItemCatalog` (19 items,
`Progression/InventoryService.cs:40`) and `CraftingService.Recipes` (4 recipes,
`Progression/EconomyService.cs:582`) are hardcoded C# tables. `items.json` and `recipes.json` are read
by `validate_content.py`, by `economy_sim.py`, and by the editor's `ContentImporter` — which only
collects ids from them. `CampaignContent.RequiredFiles` lists **neither**. So every price, mass,
stack-size, protected-ledger and arbitrage rule this project validated applied to a file the game
ignores, and the two representations agreed by luck. That is DEF-016's exact shape; the validator's own
header warns that such a drift "went unnoticed because nothing checked the path".

**Decision.**

1. **Pin the two tables together by assertion, not by convention.** `EconomyArbitrageTests` reads
   `items.json` / `recipes.json` and compares *every field of every entry* — id set, `nameKey`,
   `maxStack`, `unitMassKg`, `protectedLedger`, `sellable`, `purchasePriceSalvage`; recipe output,
   quantity, fee and each input quantity — against the tables that actually run. Mutants M3–M6 (one
   drifted price, one drifted `sellable`, one drifted fee, one drifted input quantity) are each caught,
   so the pin is real rather than decorative.
2. **Do not silently make the JSON authoritative.** Loading both files through `CampaignContent` and
   deleting the hardcoded tables is the right eventual fix, but it is an architecture change: a new
   required-content dependency, a load path that works headless *and* in Unity, and a check that no
   existing save references an item id absent from content. None of that can be verified in Unity from
   here. A parity test buys the same protection today at a fraction of the risk, so the duplication is
   recorded as **KI-046** instead of being half-migrated.
3. **Assert §10.4's sentence and QA case 17 separately.** `CraftedOutputsSellForLessThanTheirInput-
   PurchaseValue_Spec10_4` uses materials only; `CraftedOutputsAlsoStayUnderInputsPlusTheFee_QA17`
   keeps the predicate's own rule. Both Python checks now do the same, so the three implementations
   agree on what they are testing rather than quietly differing.
4. **Prove each sweep can fail.** `TheArbitragePredicateFiresOnARecipeThatWouldProfit` builds a
   deliberately profitable recipe (one polymer in, a camp kit out: sell 40 > materials 12) and requires
   the predicate to say so; `TheSweepsBelowHaveSomethingToSweep` pins the table sizes at 19 and 4,
   because a `foreach` over an empty collection passes without testing anything — which is exactly how
   an "automated arbitrage test" can exist and still prove nothing. The Python side gets the same
   treatment out of band: `validator-negative-control.log` injects a recipe that sells for 16 against
   12 of materials and a 10 fee, which the *old* check passed and the new one reports.
5. **Execute the loop, not just the arithmetic.** `BuyCraftSell_NeverCreatesCurrency_EndToEnd` grants
   materials + fee, spends the purchase value, delivers the inputs, crafts, sells, and asserts the
   wallet ends strictly below where it started — plus that the fee was charged exactly once (KI-022),
   the output landed, and the inputs were consumed rather than duplicated. A content predicate cannot
   see any of that wiring.
6. **Per-unit flooring is pinned explicitly.** §10.4 says "rounded down" per material price, and
   `CheckSell` computes `SellPrice(unit) × quantity`. Flooring the *total* instead would pay 14 for
   three polymer rather than 12, leaking 2 Salvage per stack; mutant M10 makes exactly that change and
   `SellingPaysThePerUnitFloor_NotTheFloorOfTheTotal` catches it.
7. **Selling Salvage itself is a currency-creation vector and is tested.** `salvage_bundle` is marked
   `sellable: true` in content but banks 1:1 on extraction, so selling one would turn a bundle into
   Salvage twice. `CheckSell` refuses it by category, and the fixture now asserts that refusal (mutant
   M12 removes it and is caught).

8. **The `sellable` flag is tested on an item no content exercises.** Every unsellable object in
   `items.json` is *also* `protectedLedger` or a quest/delivery object, so `CheckSell`'s two category
   refusals alone reject all nine and the `!def.Sellable` clause looks redundant. It is not: content may
   mark *any* item unsellable, and a plain `Material` is the case nothing in the catalog exercises.
   `TheSellableFlagAloneRefusesASale_WhateverTheCategory` flips `scrap_metal.Sellable` off inside a
   `try`/`finally` (the catalog is a shared static table, and NUnit runs these fixtures sequentially —
   there is no `Parallelizable` attribute in the assembly), asserts the sale is refused *with stock
   present* so the failure cannot be mistaken for missing materials, and restores the flag.
9. **Two mutants survived the first run, for two different reasons.** M12 (dropping the Currency
   refusal) survived because `salvage_bundle` costs 1, so `floor(1 × 0.4) = 0` and the later
   `unit <= 0` guard refuses it with the same `FailureReason.ItemNotUsableHere` — only the
   player-facing detail differed ("worth nothing to sell" instead of "Salvage bundles bank
   automatically at 1:1"). Asserting the detail caught it. That is the same lesson Batch L's L4 taught,
   so it is recorded as a convention: **when two refusal paths share a `FailureReason`, the test must
   assert the detail.** M11 (dropping `!def.Sellable`) survived for a different reason and was *not*
   fixed by the detail: all nine unsellable objects are caught by the category clauses, which produce
   the identical reason and the identical message, so no assertion over current content can see the
   difference. It needed point 8 — a test of the clause on an item whose category does not already
   refuse it. A survivor can mean "the test is weak" or "the content never exercises the code"; the two
   call for different fixes, and guessing wrong leaves a guard that looks tested and is not.

**Rationale.** Three checks agreeing with each other is not evidence when all three read the same
weaker rule from the same unread file. The value here is not the arithmetic — today's content passes
every version of it — but that the rule now matches the sentence, that the tables the rule reads are
the tables the game runs, and that each check has been shown to fail when it should. Keeping the
duplication (KI-046) rather than migrating it is the honest trade: a test that fails loudly on drift
beats a refactor that cannot be verified in Unity from this environment.

**Status:** Executed 2026-10-21. 12 new `EconomyArbitrageTests`; suite 254 → 266 passing, 0 warnings;
**12/12** mutation checks caught on the third run — the first reported 10/12 and the second 11/12, and
both survivors were fixed in the tests rather than waved off (points 8 and 9)
(`Docs/evidence/arbitrage-content-parity-2026-10-21/`); validator negative control demonstrates the
strengthened rule firing on a recipe the previous check passed; `validate_content.py`, `economy_sim.py`
and `formula_checks.py` clean. KI-046 opened for the underlying table duplication.

## 2026-10-21 — D-045 Relic sets come from content; the sensor loop is the first consumer of SignalRadiusM

**Context.** MAP-03 (§8.3–8.4) was the last dependency-ready M2 gap. Recon found that its four
requirement clauses were in three *different* states, and that two of them looked implemented while
being unreachable:

1. **§8.3's relic sets had no code at all.** `DiscoveryService` held a `HashSet<string>` behind an
   unvalidated `TryAddRelic(string)`: no set concept, no biome grouping, no reward keys, nothing that
   knew a set was five. `relics.json` — 25 relics, five per biome, each with a reward key,
   `protectedLedger: true` and `sellable: false` — was read by `validate_content.py` and by nobody in
   the game, because `CampaignContent.RequiredFiles` did not list it. That is KI-046's shape in a third
   table: the content that was validated was not the content that ran.
2. **§8.3's sensor ranges were composed and consumed by nothing.** `VehicleStatsResolver` composes a
   baseline `SignalRadiusM` of 80 m, `ResearchService` raises it to 140 m (tier 9, Radar I) and 220 m
   (tier 19, Radar II), and `upgrades.json` matches §11.2:726/:736 exactly. A determinism test pinned
   the numbers. The only other reference in the repo was a regression test asserting the composition.
   **No behaviour depended on it**, so both paid radar upgrades were inert.
3. **§8.4's mapping rewards and 60% finale gate are genuinely implemented** and partly tested.

**Decision.**

1. **Relics are content, and the protected ledger is the only place they live.** `relics.json` joins
   `RequiredFiles`; `CampaignContent` parses `RelicDefinition` (id, biome, nameKey, rewardKey,
   protectedLedger, sellable) and groups ids into per-biome sets, Ordinal-sorted so a capture and a UI
   always agree. `CollectRelic` validates against content: an unknown id is `ContentMissing`, never a
   silently accepted string. Set size is read from content, not hardcoded to five — §8.3 says five
   today, and content is allowed to say otherwise.
2. **A relic never becomes an item.** No cargo slot, no mass, no garage stack, nothing to sell or
   transfer or lose in a rescue. `CheckSell` cannot reach one because there is no catalog entry, which
   is a stronger guarantee than a refusal branch: §8.3's "cannot be sold or lost" holds structurally.
3. **Set completion is derived, never stored.** `IsRelicSetComplete(biome)` counts the ledger against
   the content set on every call. A persisted "set complete" flag could disagree with the relics
   actually found after a migration or a rescue; a derived answer cannot. What persists is the *reward*,
   as a claimed key.
4. **Two reward keys, per §8.4.** Each relic claims `reward.relic.<biome>.NN`; a completed set claims
   `reward.relicset.<biome>`. Both go through `ClaimedRewardLedger.TryClaim`, which pays once and
   survives reload. When cosmetic memorabilia and journal content exist, they hang off those keys — no
   second ledger, and no stat may move (asserted against eight resolved stats).
5. **The sensor loop lives in `Campaign/Map`, not `Progression`.** `Progression` cannot reference
   `CampaignContent`, so relic-set logic sits on `CampaignSession`; the sensor needs
   `MapMarkerRules.SearchAreaCenter`, which is `Campaign` too. `SensorLoop` itself is a pure static
   model taking an observer position and a radius, so it is testable with no vehicle, no session and no
   Unity — and `VehicleController` / map views only render its readings.
6. **Precision is a separate constant from range.** §8.3 gives 80 m for the pulse and 45 m for
   directional precision, and Radar I/II raise *only* the pulse range. Tying precision to the resolved
   radius would make Radar II precise at 220 m and quietly delete the search-area rule, so
   `DirectionalPrecisionRadiusM` stays 45 m at every radar tier (mutant M04).
7. **Beyond 45 m the sensor draws the marker rules' own search-area centre.** Reusing `SearchAreaCenter`
   instead of inventing a second offset means §8.3's "a search area, not exact vertical navigation" has
   one implementation, and the sensor and the exploration map cannot disagree about where to look.
8. **A missing radius falls back to the baseline — not to silence, not to unlimited range.** Content
   that forgets to compose `SignalRadiusM` must still behave like an 80 m sensor (mutants M08, M09).
   Deafening the player or revealing the whole map are both worse failure modes than the baseline.
9. **Signals are the sites content already places.** `relics.json` has no coordinates, no `sites.json`
   kind is a relic, and `vertical_slice.json` places none, so the sweep uses `Content.Sites` — relays,
   quest items, inspect targets, deliveries and routes. Relic sockets become one more signal source when
   they are placed (KI-047); the sensor needs no change.

**Alternatives considered.** Authoring 25 relic placements now was rejected: choosing defensible
positions is world-pipeline work (M3, KI-037/038), and the standing scope decision is to close
dependency-ready M2 gaps before M3. Leaving `SignalRadiusM` unconsumed was rejected: a green stat test
is not evidence a feature works, and two paid upgrades that do nothing is a live defect, not a missing
one. Putting the sensor in `Progression` was rejected on the assembly-reference rule. Storing set

## 2026-10-21 — D-046 Report §8.4's progression target as missed; do not tune the threshold or the mask

**Context.** Batch O closed §8.3. §8.4 was the remainder of MAP-03. Its reward code existed in
`DiscoveryService` and was partly covered by `CampaignSessionTests`, but three things were missing: no
test asserted `MapCoveragePercent` or `MeetsFinaleMapRequirement`, the paid-threshold index had never
been tested across a save/reload, and — most importantly — the target progression test §8.4 *explicitly
mandates* did not exist:

> "Target progression tests must show that story routes plus reasonable detours can achieve 60%;
> otherwise adjust route exposure or the threshold."

Writing it produced a result worth more than the tests around it: **the target is not met.** Playing
Q01–Q04 end to end reveals 1.22% of countable cells (112 of 9216). Adding every detour content places —
each landmark, cache, site, garage and camp socket, plus each checkpoint route walked at 32 m steps, 332
reveal stops — reaches 7.22% (665 cells). The finale needs 60%, i.e. 5530 cells.

**Why the gap is so large.** Two causes compound:

1. There are almost no story routes to drive. The slice places **one** checkpoint route
   (`route.forest.ford`, 2 checkpoints) and 15 positioned points in total, and missions Q05–Q20 have no
   placed sites at all.
2. The denominator is the whole map. `BakeCountableMask` keeps every cell whose base height is above
   `SeaLevelY`, and on the canonical seed **no cell falls below it**, so the mask counts all
   9216 = 96×96 cells. Its own doc comment says "excluding ocean/decorative cliffs"; nothing is excluded.

**Decision.**

1. **Report the miss; do not tune the number.** §8.4 offers two remedies — adjust route exposure or
   adjust the threshold. Lowering 60% would falsify a blueprint target written for the *full* game in
   order to make a *vertical-slice* test pass, and it would hide the real gap. The threshold stays 60.
2. **Do not shrink the countable mask to the slice either.** Restricting the denominator to the placed
   content's bounding box would make the metric look healthy by changing what is measured. Whether the
   canonical seed *should* have cells below sea level is a genuine world-bake question (KI-027/038), and
   it deserves an answer on its own merits, not as a way to pass a test.
3. **Record it as KI-048, scoped to the M4 finale gate.** It does not block M2: nothing in the vertical
   slice asks the player to reach 60%. It blocks the M4 finale, and both real fixes need M3 — the route
   graph (KI-030) and the bake/sea-level decision.
4. **Pin the mask's actual behaviour in a test.** `TheCountableMaskCountsEveryCell_...` asserts the mask
   equals 9216 cells. That converts a silent world-generation property into a stated one, so any future
   change to the bake is deliberate and shows up as a failing test rather than as a coverage number that
   quietly moved.
5. **Pin §8.4's literal numbers absolutely.** Every other reward and gate test derives its expectations
   from `DiscoveryService`'s constants, so a drifted constant would drag its own assertions along and
   stay green. 120 / 50 cells / 50 Salvage / 60% are asserted as literals, and the gate's crossing point
   is stated as 5530 of 9216 cells rather than as a percentage of whatever the mask happens to be.
6. **Keep the vista interaction, and assert it.** Discovering a vista landmark escrowed 220 Salvage, not
   120 — §8.1 makes a vista survey a 384 m disc, which crosses mapping thresholds. That is two correct
   rules composing, not a double payment: the landmark pays `reward.landmark.<id>` and each threshold
   pays its own `reward.map.N`. It is now a test of its own, and the pure-120 case uses a non-vista
   landmark so the two are separable.
7. **Write the save explicitly in persistence tests.** `RevealAround` only marks the autosave dirty, so
   a reload test that never calls `SaveNow()` reads the pre-mapping snapshot and appears to show a lost
   paid-threshold index. It does not: `mappingRewardsPaidThroughCount` is captured and restored
   (`CampaignSnapshot.cs:102`, `:196`; `SaveDtos.cs:117`) and mutants M12/M13 prove the test sees it.

**Alternatives considered.** Lowering `FinaleMapCoveragePercent` to ~8% so the slice passes — rejected,
it destroys the design target. Scoping the mask to placed content — rejected, it changes the metric
instead of the game. Skipping the mandated test because the slice "isn't the full game" — rejected: §8.4
asks for exactly this test, and not writing it is how a 60% gate ships unreachable. Faking coverage by
setting reveal bits directly in the progression test — rejected; it uses the real `RevealAround` path
with terrain line-of-sight, and bit-setting is used only in the gate-boundary test where the reveal
mechanism is not the subject.
